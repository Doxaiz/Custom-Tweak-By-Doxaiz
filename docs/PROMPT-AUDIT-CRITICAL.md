# Промт: НАЙДЕННЫЕ КРИТИЧЕСКИЕ ОШИБКИ (вставить первым, до задач A–V)

Этот файл — результат аудита кода проекта «Custom Tweak By Doxaiz» на `main = bd231cf`
(версия 0.4.1, 544 теста зелёные). Аудит искал не «что добавить», а **что уже может навредить**
пользователю или его компьютеру. Найдено шесть настоящих проблем, одна из них — критическая.

**Правило работы с этим файлом:** сначала закрываются C1–C3, и только потом берутся задачи A–V из
остальных промтов. Это не новые функции, это исправления. Каждое — с тестом, который падает до
исправления и проходит после.

Ничего из описанного «на глаз» я не применял: рабочие правки откачены, дерево чистое на `bd231cf`.
Ниже — что менять и как проверять.

---

## C1. КРИТИЧНО: любой пользователь компьютера может менять Windows через службу

**Где.** `src/PingForge.Service/EngineDispatcher.cs`, строки ~43–50:

```csharp
if (descriptor.NeedsElevation && !_operations.IsElevationAvailable)
{
    return EngineResponse.Failure(request.Id, "…нет прав администратора…");
}
```

**В чём ошибка.** Проверяются права **службы**, а не того, кто к ней подключился. А служба работает
от `LocalSystem` (`install-service.ps1`) и в `ServiceProgram.cs` создаётся с жёстко зашитым
`isElevationAvailable: true`. Значит, эта проверка **всегда проходит**.

Канал при этом открыт для `S-1-5-4` (интерактивный пользователь, `ServiceSecurityPlan.Grants`) с правом
`ReadWrite`, а сервер канала права клиента не проверяет вообще: в `EnginePipeServer.cs` нет ни
`RunAsClient`, ни `WindowsIdentity`.

**Сценарий атаки (реальный).** На компьютере два человека: владелец — администратор, и, например,
ребёнок, гость или второй пользователь без прав. Второй пользователь запускает у себя любой скрипт,
подключается к `\\.\pipe\PingForge.Engine.v1` (канал ему разрешён) и отправляет
`{"id":"1","command":"apply-preset","args":{"preset":"low-latency"}}`. Служба применяет твики
**от имени SYSTEM**. То же самое — с `repair-network`, `rollback` и живой оптимизацией.
Это повышение привилегий без единого запроса UAC.

Дополнительно: любой процесс, запущенный от *того же* пользователя (включая вредоносный скрипт),
может менять систему без подтверждения, потому что подтверждение спрашивает **окно**, а не служба.
Канал — отдельная точка входа, и она сейчас без проверки.

**Как исправить (проект решения, проверенный на компиляцию вчерне).**

1. `EngineDispatcher.HandleJsonAsync` и `HandleAsync` получают параметр
   `bool clientIsAdministrator` и проверяют **его**, а не `IsElevationAvailable`.
   `IsElevationAvailable` оставить второй, независимой проверкой (служба реально может не иметь прав).
   Текст отказа: «Команда … выполняется только для администратора этого компьютера. … Права службы
   здесь не помогают: она работает от имени системы, поэтому проверяется именно ваша учётная запись».
2. `EnginePipeServer`: после `WaitForConnectionAsync` определить права клиента:

```csharp
bool isAdmin = false;
try
{
    pipe.RunAsClient(() =>
    {
        using WindowsIdentity identity = WindowsIdentity.GetCurrent(); // внутри — токен клиента
        isAdmin = new WindowsPrincipal(identity).IsInRole(WindowsBuiltInRole.Administrator);
    });
}
catch (Exception ex) when (ex is IOException or UnauthorizedAccessException
    or System.ComponentModel.Win32Exception or InvalidOperationException)
{
    _log($"Не удалось определить права клиента ({ex.GetType().Name}) — считаю, что прав нет.");
    isAdmin = false; // отказ безопаснее разрешения
}
```

   И передавать `isAdmin` в диспетчер.
3. **Журнал отказов.** Каждый отказ по правам писать в `service.log` с именем и SID клиента
   (`WindowsIdentity.GetCurrent().Name/User` внутри `RunAsClient`) — иначе нет следов попыток.
4. Тесты (падают на текущем коде, проходят после):
   - без прав `apply-preset` / `apply-tweaks` / `rollback` / `repair-network` / `realtime-start`
     → отказ с текстом «только для администратора», и **операция не вызвана** (двойник `IEngineOperations`
     остался пустым);
   - без прав работают `ping`, `capabilities`, `status`, `journal-tail`, `system-state`, `realtime-stop`
     (иначе «вернуть как было» станет недоступным обычному пользователю — это тоже ошибка);
   - с правами всё работает как раньше;
   - `IsElevationAvailable = false` при админе-клиенте → второй, отдельный отказ про службу.
5. Живая проверка на раннере: создать локального пользователя без прав, запустить от него
   небольшой консольный клиент к каналу (или PowerShell с `NamedPipeClientStream`), отправить
   `apply-preset`, увидеть отказ; в `service.log` — запись с именем клиента. Снимок и журнал в артефактах.

## C2. Канал открыт шире, чем нужно: `S-1-5-4` — это любой интерактивный вход

**Где.** `src/PingForge.Service/ServiceSecurityPlan.cs`, `Grants`: `LocalSystem`, `Administrators`,
`InteractiveSid` (`S-1-5-4`).

**В чём ошибка.** `S-1-5-4` — не «владелец компьютера», а «любой, кто вошёл в систему интерактивно»:
второй пользователь, гостевой сеанс, сеанс по RDP. Вместе с C1 это и даёт повышение привилегий.
Само по себе разрешение для интерактивного пользователя нужно (окно работает без админа), но его
надо сузить.

**Как исправить.**

1. Оставить в ACL `LocalSystem` и `Administrators`.
2. Для чтения состояния обычному пользователю **не открывать полный канал**: сделать второй канал
   `\\.\pipe\PingForge.Engine.ReadOnly.v1` с правом только на команды `ping`, `capabilities`, `status`,
   `journal-tail`, `system-state`. Диспетчер для него жёстко ограничивает список команд (а не
   полагается на флаг `NeedsElevation`).
3. Основной канал — только `Administrators` + `LocalSystem`; окно, запущенное без прав, подключается
   к read-only каналу и показывает «доступны просмотр и остановка, для изменений запустите от имени
   администратора» (этот текст уже есть в продукте).
4. `realtime-stop` должен работать и без прав — но идти через read-only канал с отдельным разрешением
   «снять свои изменения» (это не изменение чужих настроек, а откат).
5. Тесты: в `Grants` нет `S-1-5-4`; read-only диспетчер отклоняет `apply-preset` даже если клиент
   администратор; список разрешённых read-only команд задан **одним массивом** и совпадает с
   документацией (проверка «нет расхождения текста и кода»).
6. Живая проверка: канал создаётся, обычный пользователь подключается к read-only и видит статус,
   попытка записи в основной канал — отказ на уровне Windows (не доходит до диспетчера).

## C3. Настройки теряют данные: два процесса пишут один файл без блокировки

**Где.** `src/PingForge.App.ViewModels/JsonFileSettingsStore.cs` (строки ~42, 76–78) и
`src/PingForge.Service.Host/ServiceSettings.cs` (строки ~55–75).

**В чём ошибка.** Оба делают «прочитать весь файл → изменить своё поле → записать временный →
переименовать». Окно пишет `SetupCompleted`, `GamePaths`, профиль; служба пишет `PerfProfile`.
Если они делают это одновременно, **последний записавший затирает поле другого**: например, человек
меняет профиль в окне, а служба в этот момент сохраняет свой — и пути к играм или ответы мастера
исчезают. Переименование атомарно только для одного писателя.

**Как исправить.**

1. Единая запись через именованный мьютекс (`Global\PingForge.Settings.v1`) вокруг
   «прочитать → изменить → записать» в **обоих** местах.
2. Перед записью — резервная копия `settings.json.bak` (одна, перезаписывается), чтобы откатить
   испорченный файл.
3. Если файл не читается (битый JSON) — не затирать его: переименовать в `settings.json.broken-<дата>`
   и начать с чистого, сказав об этом в журнале.
4. Тесты: два «писателя» в цикле по 100 итераций не теряют поля друг друга (в тесте — мьютекс и
   файлы во временной папке); битый файл не пропадает, а переименовывается; после записи `.bak`
   содержит предыдущую версию.

## C4. У приложения нет манифеста: DPI и права не объявлены

**Где.** В `src/PingForge.App` **нет `app.manifest`**, в `.csproj` нет `ApplicationManifest`.

**Следствия.** При масштабе 125/150 % окно может мылиться (нет `PerMonitorV2`); нет явного
`asInvoker` — то есть поведение зависит от настроек системы и от того, как запущен файл. Для продукта,
который принципиально «ничего не делает без нажатия», это ещё и вопрос доверия: права должны быть
объявлены, а не подразумеваться.

**Как исправить.** Добавить `app.manifest` с `requestedExecutionLevel level="asInvoker" uiAccess="false"`
и `dpiAwareness = PerMonitorV2` (+ `longPathAware`), прописать в `.csproj`. Тест читает файл и
проверяет оба значения. Живая проверка: снимок при 150 % — текст чёткий, ничего не обрезано
(это же нужно задаче N).

## C5. Версии окна и службы не сверяются — «не отвечает» вместо «разные версии»

**Где.** `EngineClient` получает `protocolVersion` и `appVersion`, но **нигде не сравнивает** их ни со
своей версией, ни с `EngineProtocol.Version`.

**Следствия.** Обновление поверх установленной версии (или portable поверх установки) даёт окно,
которое говорит «служба не отвечает», хотя служба жива и просто другой версии. Пользователь
переустанавливает всё подряд.

**Как исправить.** Три исхода: совпало; **протокол не совпал** → окно не отправляет меняющие команды
и показывает «Служба другой версии: окно X, служба Y, протокол A/B — запустите установщик заново»;
версия отличается, протокол тот же → предупреждение и строка в «О программе». Тесты: несовместимый
протокол → меняющие команды не уходят; в отказе названы обе версии. Живую проверку делать
с подменённой «старой» службой.

## C6. Защитный код, который никто не вызывает

**Где.** `ServiceSecurityPlan.HasForbiddenIdentity()` — объявлен, но **не вызывается ни из службы,
ни из тестов**. Это значит: если кто-то завтра добавит в `Grants` `Everyone`, `Guests` или
`ANONYMOUS LOGON`, сборка и тесты этого **не заметят**.

**Как исправить.** Вызывать проверку при старте службы (`PipeAclFactory.Build()` или
`ServiceProgram`): если в таблице есть запрещённый SID — не открывать канал и записать причину
в журнал. Плюс тест: таблица с `S-1-1-0` не проходит проверку, текущая — проходит.

## Что проверено и работает — не переделывать

Чтобы не тратить время на повторный аудит:

- **Предел кадра есть** (`EngineProtocol.MaxFrameBytes`) и проверяется тестами — службу нельзя уронить
  гигантским кадром.
- **Аргументы `route` собираются списком и валидируются** (`RouteCommandBuilder`: `IsValidAddress`,
  `IsValidMetric`, внутренний адрес и broadcast запрещены) — подстановки команды нет.
- **ACL: наследование отключено**, `Everyone` не приезжает из окружения, вход по сети запрещён
  отдельным deny-правилом (`PipeAclFactory`). Проблема именно в широте `S-1-5-4` (C2), а не в
  отсутствии deny.
- **Каталог твиков проходит аудит запретов** (`CatalogSafetyAudit`): Defender, UAC, Windows Update,
  подписи драйверов — в каталоге их нет, это проверяется тестом.
- **Снапшоты хранятся в SQLite, не файлами** — подстановки пути через id снапшота нет.
- **Канал обслуживает одно соединение за раз** — гонки между двумя меняющими командами нет.
- Тесты 544 зелёные, живая сборка и установка проверены на Windows.

## Порядок работ

1. **C1** — критично, без него остальное вторично. Требует правки диспетчера, сервера канала и ~4 тестов.
2. **C2** — следом: сузить ACL и ввести read-only канал (это меняет и окно: без прав оно подключается
   к read-only).
3. **C3** — мьютекс и резервная копия настроек.
4. **C4**, **C5**, **C6** — быстрые, каждая на полчаса-час.
5. Только после этого — задачи A–V из остальных частей промта.

## Связанные задачи из других частей промта

- **T** (удаление без следов) — та же тема «программа ушла, изменения остались»; C1/C2 её не заменяют.
- **O** (версии окно↔служба) — C5 это её техническое ядро; делать вместе.
- **Q** (логи, дамп) — журнал отказов из C1 требует ротации, иначе файл растёт без предела.
- **U** (целостность базы) — снапшоты; с C3 не пересекается (там `settings.json`, здесь SQLite).
