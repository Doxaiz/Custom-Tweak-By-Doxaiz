## 2. Найдено при проверке: C7 — проверка прав клиента не работает

Файл `src/PingForge.Service.Windows/PipeClientInspector.cs`, две ошибки в одном месте.

### 2.1. Взята не та функция Win32

```csharp
private static bool TryGetClientProcessId(NamedPipeServerStream pipe, out int processId)
{
    processId = 0;
    return GetNamedPipeServerProcessId(pipe.SafePipeHandle.DangerousGetHandle(), ref processId);  // ← ошибка
}
```

В документации Microsoft разделение прямое: **сервер** вызывает `GetNamedPipeClientProcessId`,
**клиент** вызывает `GetNamedPipeServerProcessId` (подтверждение: BleepingComputer, разбор IPC —
«the server can call GetNamedPipeClientProcessId; the client can call GetNamedPipeServerProcessId»,
и Win32 API — «GetNamedPipeServerProcessId: retrieves the server process identifier»).

Наш код — это сервер. Значит, `GetNamedPipeServerProcessId` возвращает **свой собственный** PID, то есть
процесс службы. Дальше код открывает токен службы (LocalSystem) и спрашивает «администратор ли он» —
ответ всегда «да». Проверка «кто подключился» на самом деле не проверяет никого.

### 2.2. Взята не та константа прав токена

```csharp
private const uint TokenQueryLimited = 0x1000;   // ← ошибка: 0x1000 — это PROCESS_QUERY_LIMITED_INFORMATION
```

Права на **токен** — это `TOKEN_QUERY = 0x0008`. `0x1000` в маску `TOKEN_ALL_ACCESS` (`0xF01FF`) не входит,
поэтому `OpenProcessToken(..., 0x1000, ...)` завершается с `ERROR_ACCESS_DENIED`. Комментарий
«QUERY_LIMITED_INFORMATION: достаточно, чтобы спросить токен» описывает права на **процесс**, а не на токен.

### 2.3. Что это даёт вместе

- Если первая ошибка «срабатывает»: PID = PID службы → токен LocalSystem → `IsAdministrator = true`
  **для любого клиента** → в журнале появляется ложная строка
  «клиент: NT AUTHORITY\SYSTEM (SID S-1-5-18), процесс <PID службы>, права администратора: есть».
  Второй уровень защиты фиктивный, обещанного «в журнале имя и SID настоящего клиента» нет.
- Вторая ошибка перебивает первую: токен не открывается → `PipeClientIdentity.Unknown` →
  `IsAdministrator = false` **для всех, включая настоящего администратора**.

Второй сценарий — не «дыра», а **поломка продукта**: в `EngineDispatcher` первая же проверка
`if (!clientIsAdministrator)` отвечает отказом, поэтому «Применить твики», пресеты, откат, починка сети
и живая оптимизация **не выполнятся даже у администратора**. Сообщение при этом будет обидное:
«у процесса, который её прислал, прав администратора нет».

### 2.4. Почему это не заметили тесты и прогоны

- Тесты диспетчера передают `clientIsAdministrator: true` вручную — они проверяют логику отказа,
  а не определение прав. На Linux P/Invoke не выполняется вовсе.
- Живой прогон (`EngineSmoke`, walkthrough) делает **только читающие** команды; кнопка «Оптимизировать»
  на раннере честно упирается в «игра не найдена» **до** любой меняющей команды. То есть путь
  «применить изменения» на живой Windows не проверялся ни разу — это и есть корень.

**Оценка важности.** C1 закрыт ACL канала: обычный пользователь до основного канала просто не дотянется,
так что повышения привилегий сейчас нет. Но второй слой защиты не работает, журнал врёт, а менять
настройки не может даже администратор. Это надо исправить до любой новой функциональности.

## 3. Что сделать (задача C7)

### 3.1. Исправление

1. `TryGetClientProcessId` → `GetNamedPipeClientProcessId` (и переименовать локальную переменную,
   комментарий тоже: сейчас там написано `GetNamedPipeServerProcessId`).
2. `TokenQueryLimited` → `0x0008` с правильным именем `TokenQuery` и комментарием: «TOKEN_QUERY —
   спросить сведения о токене; прав на процесс почти не нужно».
3. Ничего не менять в логике «ошибка → прав нет»: она правильная.

### 3.2. Тесты-сторожа (падают на текущем коде)

На Linux нельзя вызвать Win32, поэтому защищаемся текстом и живой проверкой:

1. **Текстовый сторож** (по образцу теста манифеста): файл `PipeClientInspector.cs` обязан содержать
   `GetNamedPipeClientProcessId` и `const uint TokenQuery = 0x0008`; и **не** содержать
   `GetNamedPipeServerProcessId`. Такой тест упал бы на текущем коде.
2. **Живая проверка личности на раннере (одна учётка).** Добавить в ответ `ping` поля
   `clientName`, `clientSid`, `clientIsAdmin` — их заполняет служба по `PipeClientInspector`.
   В `tools/PingForge.EngineSmoke` (или отдельным флагом `--expect-identity`) проверять:
   - `clientName` равен имени пользователя раннера (не `NT AUTHORITY\SYSTEM`);
   - `clientSid` не равен `S-1-5-18`;
   - `clientIsAdmin = true` для запуска от администратора.
   Это ловит **обе** ошибки сразу: первая даёт SYSTEM, вторая — `false`.
3. **Живая проверка отказа (две учётки)** — то, что в отчёте честно названо невыполненным. Она
   выполнима на раннере:
   - `net user pfcheck '<пароль>' /add` (пользователь без прав администратора);
   - запустить `PingForge.EngineSmoke --try-apply` **от этого пользователя** через
     `Start-Process -Credential (New-Object pscredential ...)` — это `CreateProcessWithLogonW`,
     работает без интерактивного входа;
   - ожидание: подключение к основному каналу отклонено ACL **или** отказ диспетчера; в
     `service.log` — строка с SID этого пользователя (`S-1-5-21-...`), а не SYSTEM;
   - после проверки `net user pfcheck /delete`.
   Команда для попытки должна быть **безопасной**: `apply-tweaks` с заведомо пустым списком или
   `--dry-run`, чтобы даже при ошибке проверки прав ничего не менялось. Лучше — новый флаг смоука
   `--try-apply`, который шлёт `apply-tweaks` с кодом несуществующего твика: если права проверены
   верно, ответ будет «только для администратора», а не «твик не найден».
4. **Живая проверка «админ может».** На раннере (он администратор) применить один безобидный твик
   через основной канал и увидеть «применено», затем откатить. Это закрывает дыру «путь применения
   на живой Windows не проверялся ни разу». Твик — самый безобидный из каталога, с откатом из снапшота.

### 3.3. Документы

- `docs/КАНАЛЫ-СЛУЖБЫ.md`: дописать, что личность клиента определяется по процессу клиента
  (`GetNamedPipeClientProcessId`) и что имя/SID клиента пишутся в журнал при каждом подключении и отказе.
- README: исправить формулировку «две независимые проверки» — она верна по замыслу и станет верной по
  факту после C7.

### 3.4. Критерии готовности C7

- [ ] Текстовый сторож падает до правки и проходит после
- [ ] Прогон: `service.log` содержит имя раннера и его SID, а не SYSTEM
- [ ] Прогон: пользователь без прав получает отказ, отказ есть в журнале с его SID
- [ ] Прогон: администратор применяет безобидный твик и откатывает его
- [ ] Тестов не меньше 599, все зелёные; сборка 0 предупреждений
- [ ] В отчёте — честно: «оба бага были невидимы тестам, потому что тесты подставляли флаг руками»

## 4. После C7 — задача A (свои игры), как и планировалось

Кратко, полное описание — в `docs/PROMPT-ALL.md`, задача A:

1. Кнопка «Добавить игру» в разделе «Игры»: выбор `.exe`, отображаемое имя, проверка файла.
2. Хранение в общем `settings.json` (через `SharedSettingsFileWriter` — он уже есть после C3):
   `CustomGames: [{ "ProcessName": "...", "TitleRu": "..." }]`.
3. Служба читает список терпимо (нет файла / битый JSON → 20 встроенных игр, строка в журнал).
4. Детектор отдаёт свою игру как `DetectedGameFlow` с `AntiCheatStatus.Untested` и пометкой
   «своя игра: анти-чит неизвестен».
5. Удаление и переименование своих игр; встроенные 20 не удаляются.
6. Тесты: своя игра матчится; битый список не ломает запуск; удаление возвращает «кандидат, а не игра»;
   встроенные на месте; запись через общий писатель не теряет поля окна (после C3 это уже проверено,
   но повторить на новом поле).
7. Живая проверка: добавить карточку в окне, увидеть её в списке, удалить. Обнаружение потока
   проверяется тестами — на раннере игры нет, и выдумывать её нельзя.

## 5. Порядок и правило

**C7 → A → B → T → F → K → L → P → U → V**, затем остальные D, E, G, H, J, M, N, C, R, S.

Правило, которое этот раунд доказал на практике: **любой код, который работает только на Windows,
обязан иметь живую проверку с утверждением на реальном раннере — а не только тест с подставленным
значением.** Иначе «зелёные 599» будут означать ровно то, что означали здесь: ничего.
