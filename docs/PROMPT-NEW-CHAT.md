## 1. Что это за продукт

Приложение для Windows в духе ExitLag: помогает игровому соединению — находит запущенную игру,
измеряет задержку до её сервера, применяет сетевые действия (маршрут, приоритет пакетов), держит
контроль и умеет вернуть всё как было. Плюс оптимизация Windows: каталог твиков с описанием
каждого, пресеты, ручной выбор, анализ сети, журнал изменений, снапшоты.

Название в интерфейсе и в файлах — **«Custom Tweak By Doxaiz»**. Пространства имён, пути и имя
репозитория **не переименовывать**.

Ключевое правило продукта: **при запуске программа ничего не меняет**. Любое изменение — только
по нажатию кнопки, с подтверждением и снапшотом.

## 5. Правила честности (главное отличие проекта)

1. **Числа только измеренные.** «Пинг снизился с X до Y мс» — только если это записано в замере.
   Иначе — «заметного выигрыша нет» или «стало хуже, причина в маршруте». Неизмеримо — это
   честный результат, а не ноль.
2. **Не угадывать имена игр по exe.** Процесс не из каталога — «кандидат», а не игра. Пользователь
   должен видеть имя процесса и адрес, а не выдуманное название.
3. **Отказ объясняет причину и что делать.** Не «не получилось», а «нет прав администратора —
   измените запуск» / «не задан альтернативный узел — выберите его в настройках».
4. **Ничего не скрывать при откате.** Если что-то не удалось снять, так и написать.
5. **Числа в README и в интерфейсе должны совпадать с тем, что реально прогнано.**

## 7. Текущая задача: следующий раунд (0.5.0)

В коде есть два места, где программа сама себе противоречит: она обещает то, чего пользователь
не может сделать. Плюс третья задача — сделать результат проверяемым. Все три связаны.

### Задача A. «Мои игры»: добавить игру, которой нет в списке

Сейчас отказ честно говорит «добавьте её в список известных игр», но добавить негде: каталог из
20 игр зашит в код (`GameProcessCatalog`, `DefaultGames`), а служба строит его как
`new GameProcessCatalog()` в `ServiceProgram.cs`.

Требования:

1. В разделе «Игры» — кнопка **«Добавить игру»**: выбрать `.exe`, задать отображаемое название.
   Проверить, что файл существует и заканчивается на `.exe`; иначе — понятный отказ.
2. Своя игра сохраняется в **общий файл настроек** `C:\ProgramData\PingForge\settings.json`
   (поле вида `CustomGames: [{ "ProcessName": "...", "TitleRu": "..." }]`). Файл один на окно и
   службу: окно пишет, служба читает терпимо (нет файла / битый JSON — работаем с 20 известными,
   пишем строку в журнал службы, не падаем). Образец терпимого чтения — `ServiceSettings.cs`.
3. Служба передаёт пользовательские игры в `GameProcessCatalog` при сборке сетевой платформы.
4. Детектор отдаёт такую игру как `DetectedGameFlow` с `AntiCheatStatus.Untested` и в интерфейсе
   пометка: **«своя игра: анти-чит неизвестен»**. Никаких обещаний безопасности.
5. Можно удалить свою игру и переименовать. Встроенные 20 игр удалить нельзя.
6. Тесты: своя игра матчится детектором; битый/пустой список не ломает запуск; неверный путь —
   отказ; удаление возвращает поведение «кандидат, а не игра»; встроенные игры на месте.
7. Живая проверка: добавить карточку в окне, увидеть её в списке, удалить. Само обнаружение
   потока проверяется тестами (на раннере игры нет — и мы это не выдумываем).

### Задача B. Серверы маршрутизации: выбор узла, замер путей, честный отказ

**Что есть сейчас.** Действие «маршрут для игрового сервера» написано и покрыто тестами, но
`RouteTarget` в `WindowsGameNetworkPlatform` **никто не заполняет**. Поэтому в бою оно всегда
отказывает: «Маршрут не изменён: не задан альтернативный узел». То есть живая оптимизация умеет
применять только DSCP — половину заявленного.

**Чего нет и не будет.** У проекта нет своей сети узлов, как у ExitLag: мы не арендуем серверы по
миру и не обещаем «оптимизацию через нашу сеть». Врать про инфраструктуру нельзя. Поэтому «сервер
маршрутизации» в этом продукте — это **узел, который у пользователя уже есть** (второй шлюз, VPN-адаптер,
свой VPS), а программа честно измеряет, короче ли через него путь, и не включает ничего молча.

#### B1. Список узлов (откуда берутся кандидаты)

1. **Автопоиск из системы:** все шлюзы всех активных адаптеров из таблицы маршрутов (у каждого —
   имя адаптера и тип), плюс шлюзы VPN-адаптеров (WireGuard, OpenVPN, IKEv2 и подобные — по имени
   адаптера, без попыток подключиться к ним самим).
2. **Ручной ввод**: адрес узла и, необязательно, подпись. Валидация IP, мусор не сохраняется.
3. **Источник подписан честно**: «второй шлюз», «VPN-адаптер “WireGuard”», «введён вручную».
   Придуманных «серверов PingForge» в списке быть не может — это проверяется тестом на содержимое.
4. Узлы хранятся в общих настройках (`RoutingNodes`) рядом с уже выбранным узлом по умолчанию.

#### B2. Замер путей до выбора (главное)

Нельзя просто поставить маршрут и сказать «стало лучше». Порядок:

1. Замер **прямого пути** до адреса игрового сервера (уже есть: `RouteProbeService`).
2. Для каждого узла-кандидата — **временный** маршрут `/32` только на этот адрес, замер тем же
   методом, немедленный откат временного маршрута.
3. Сравнение по медиане RTT, затем по джиттеру и потерям. Побеждает лучший; **если ни один узел не
   лучше прямого — так и написать: «прямой путь короче на N мс, ничего не меняем»**.
4. Временные маршруты не остаются: после замера таблица маршрутов должна совпадать с исходной
   (проверка — перечитыванием, как в `RouteForGameActionRunner`).
5. Замер идёт только пока идёт оптимизация и только на адрес сервера игры — не «на весь интернет».

#### B3. Применение и выбор

1. В «Настройках» — блок **«Сервер маршрутизации»**: список узлов с колонками «узел», «источник»,
   «медиана RTT через него (если замер был)», кнопка «Измерить все пути», выбор узла по умолчанию
   и режим «выбирать лучший автоматически».
2. Автовыбор применяется **только к адресу игрового сервера** (`/32`) и только когда пользователь
   нажал «Оптимизировать»; по умолчанию его нет.
3. Рядом с блоком — честный текст: «Через чужой узел трафик идёт через третью сторону. Часть игр
   (например Destiny 2) блокировала аккаунты за смену региона — решайте осознанно».
4. Пока узла нет — действие по-прежнему отказывает, но отказ подсказывает, где выбрать узел.

#### B4. Тесты и проверка

1. Узел из настроек доходит до платформы и применяется; без узла — прежний честный отказ.
2. Мусор вместо IP не сохраняется; в списке автопоиска не бывает выдуманных «серверов PingForge».
3. «Лучший узел» выбирается по медиане; при равных — по джиттеру; при отсутствии выигрыша —
   результат «прямой путь лучше» и **ни одного изменения в системе**.
4. Временные маршруты замера всегда откатываются, даже если замер упал с исключением (проверка:
   таблица после = таблица до).
5. Чужой маршрут не перезаписывается.
6. Живая проверка: блок отображается, настройка переживает перезапуск окна, «Измерить все пути»
   на раннере честно говорит, что кандидатов кроме шлюза нет. Сам переезд трафика через второй канал
   на раннере не проверяем — его там нет.

### Задача D. Не только DNS: регионы игр и честная маркировка DNS

**Проблема.** Сейчас «улучшение» легко скатывается к подмене DNS, хотя подмена DNS **не снижает пинг
в матче**: она ускоряет только резолв имени и вход в игру. Пинг в игре определяется маршрутом до
сервера. Кроме того, справочник `GameRouteCatalog` (20 игр с регионами, 5 бесплатных DNS, 8 типов
пути) **нигде не используется** — данные есть, а человек их не видит.

Требования:

1. **Регионы игры — в интерфейс.** В разделе «Игры» у карточки — «Где серверы этой игры»: регионы из
   `GameRouteCatalog.Targets` и честная приписка, что конкретный сервер выбирает матчмейкер, а
   программа измеряет уже выданный. Программа регион не подменяет и игру за пользователя не настраивает —
   она объясняет, что выбрать в самой игре, и меряет результат.
2. **DNS — отдельная категория с честной подписью.** В «Твиках» и в блоке анализа DNS: «влияет на
   скорость входа, а не на пинг в матче». Никаких «DNS снизил пинг на N мс» — такого измерения не бывает.
3. **Список бесплатных резолверов виден человеку** (данные уже есть в `GameRouteCatalog.FreeDnsRoutes`):
   Cloudflare `1.1.1.1`/`1.0.0.1`, Яндекс `77.88.8.8`/`77.88.8.1`, Google `8.8.8.8`/`8.8.4.4`,
   Quad9 `9.9.9.9`/`149.112.112.112`, AdGuard `94.140.14.14`/`94.140.15.15`. Подпись: «выбор входа,
   не ускоритель пинга». Результат берётся из `DnsResolverBenchmarker`, а не из прозы.
4. **Типы пути (`PathKinds`) — в интерфейс**: прямой путь, IPv6, кабель, настройки роутера, второй
   канал, свой релей на VPS, публичный игровой VPN, «бесплатные ускорители». С ценами и уровнем
   безопасности, как они уже описаны в коде. Пункт «бесплатные ускорители» остаётся с пометкой «не советуем».
5. Тесты: в интерфейсе есть текст «DNS не снижает пинг в матче»; регионы каждой игры из каталога
   отображаются и не придумываются для игр, которых нет в каталоге; ни в одном тексте программы нет
   утверждения «DNS снизил пинг»; список резолверов совпадает с данными каталога.
6. Правка данных в `GameRouteCatalog` считается изменением текста для пользователя: если меняешь
   регионы — проверь, что не обещаешь того, чего игра не публикует.

### Задача C. Отчёт о сессии (файл, по кнопке)

Требования:

1. Кнопка **«Сохранить отчёт»** (в «Журнале» или на главной): сохраняет файл `.md` (или `.txt`)
   через диалог выбора места.
2. В отчёте: дата и время, версия программы, версия Windows, права администратора (да/нет),
   найденный поток (игра, процесс, адрес:порт) или честное «игра не найдена», замеры «до/после»
   с методом замера, применённые действия, что откатилось и что нет, хвост журнала.
3. Никуда не отправляет: это файл, который человек сам решает передать. Это не телеметрия.
4. «Не измерено» вместо нулей; никаких «улучшено на N %», если замер не удался.
5. Тесты: отчёт собирается из снимка и журнала, поля не выдумываются, при отсутствии замера
   стоит «не измерено», а не `0`.
