## 2. Раунд аудита: C1–C6 сделаны и проверены живыми прогонами (PR №1)

Порядок обязателен: сначала C1–C6, потом задачи A–V из `docs/PROMPT-ALL.md`. Новая задача — только
после того, как предыдущая подтверждена живым прогоном на Windows; одних зелёных тестов мало.

1. **C1 (критично) — служба больше не меняет Windows за любого пользователя.** Канал службы
   (`\\.\pipe\PingForge.Engine.v1`) доверял своим собственным правам (LocalSystem), а не правам того,
   кто подключился: любой локальный пользователь мог дать команду `apply-preset`/`rollback` и выполнить

## 3.1 Маршрутизация: живой фейловер (сделано в коде, ждёт прогона)

Что было на самом деле, а не в описании:

- `RoutingPathOptionsProvider.GetOptionsAsync` **всегда возвращал пустой список**: оптимизатор получал
  «пути нет» на каждом плохом окне, и живое переключение не могло случиться ни разу. Резерв
  запоминался (`LastSecondaryRoute`), но применить его было нечем.
- Порядок в `RealtimeOptimizer.TrySwitchPathAsync` был «сначала добавить новый маршрут, потом снять
  прежний». Исполнитель не перезаписывает уже стоящий `/32` (защита от чужих маршрутов), свой прежний
  он тоже не перезапишет — то есть переключение осталось бы на старом узле, даже если бы вариант был.
- Тексты «переключение за 1–2 с» в интерфейсе и журнале были неправдой: по умолчанию решение требует
  трёх подряд плохих окон контроля (~6 с при замере раз в 2 с).

Что сделано:

| Место | Изменение |
|---|---|
| `RoutingPathOptionsProvider` | отдаёт измеренные варианты: основной путь (победитель) и резерв; кэш решения (240 с) возвращает те же варианты, а не пустой список; ручной выбор узла тоже даёт вариант, плюс второй — если включён мультипуть |
| `RoutePathComparisonService` | резервом для переключения считается только узел, который сам выигрывает у прямого пути (`NotableImprovementMs`); узел хуже прямого в резерв не берётся, и это сказано в `LastMultipathRu` |
| `OptimizationActionDescriptor` | новое необязательное поле `RouteNextHop`: узел едет в самом действии |
| `RouteForGameActionRunner` | узел берётся из действия, «текущая цель» платформы — только запасной путь |
| `RealtimeOptimizer.TrySwitchPathAsync` | снять прежний `/32` → поставить новый → при отказе вернуть прежний и сказать об этом; путь, где уже было хуже, второй раз не выбирается (антифлаппинг) |
| `RoutingSettingsViewModel`, `CHANGELOG.md` | тексты про переключение приведены к тому, что программа делает |

Шаг 2 — честность самих замеров (сделано в коде, ждёт прогона):

| Было | Стало |
|---|---|
| прямой путь мерился один раз в начале, узлы — после | две серии вперемешку: прямой → узлы → снова прямой → узлы (`MeasurementRounds = 2`) |
| победа при выигрыше ≥ 0,5 мс | победа при выигрыше ≥ максимума из 0,5 мс и разброса серий (`RequiredGainMs`); в вердикте — «Разброс серий замера ±N мс» |
| одна серия узла выдавалась за медиану | неудавшаяся серия отменяет путь: «серия 2 из 2: путь не подтверждён» |
| узел, чей временный маршрут не встал в очередной серии, оставался «измеренным» по первой серии | вторая серия без маршрута тоже отменяет путь |

Цена — замер идёт примерно вдвое дольше (каталог `route-measure`: 240 с таймаут, запас есть); об этом честно
сказано в подтверждении «Измерить все пути».

Шаг 3 — «нет ли пути быстрее» (сделано в коде, ждёт прогона):

| Было | Стало |
|---|---|
| переключение только при просадке; если текущий путь в норме, альтернативы не перепроверялись | раз в 90 хороших окон (≈3 мин) и не чаще раза в 5 минут — сравнение измеренных медиан; уходим только при выигрыше ≥ 3 мс и ≥ разброса серий |
| вариантов для переключения было два (победитель + один резерв) | вариантами становятся все измеренные узлы, которые сами быстрее прямого пути, по порядку медианы |
| у решений не было чисел: «переключились, потому что так решили» | `RealtimePathOption.MedianRttMs`/`SpreadMs` — числа той же сессии замеров; вердикт называет разницу и порог |
| путь, с которого ушли «по скорости», не отличался от «провалившегося» | ушли по скорости — прежний путь остаётся рабочим кандидатом; ушли из-за просадки — в него не возвращаемся |
| если узел перестал помогать, об этом молчали | «свежие замеры не нашли узла быстрее прямого пути» + напоминание, что снять маршрут можно остановкой (сама оптимизация маршрут на ходу не снимает) |
| переключения могли идти одно за другим | пауза 5 минут после любого перехода (`EffectiveRouteUpgradeCooldown`) |

Честно: это не «AI выбирает маршрут» и не мультипуть с дублированием пакетов, как у ExitLag/LagoFast —
PingForge не имеет своих серверов и не ставит драйвер, который дублировал бы пакеты. Всё, что делает
программа, — измеряет пути до адреса игры и меняет маршрут `/32`; обещания ускорителей про «0 % потерь»
здесь не повторяются.

Шаг 4 — смена сервера посреди сессии (сделано в коде, ждёт прогона):

| Было | Стало |
|---|---|
| маршрут `/32` оставался на адресе прежнего матча; живой поток «переставал измеряться», и программа говорила о деградации там, где сменился сервер | раз в 15 окон перечитываем таблицу соединений; прежний адрес исчез, появился новый → маршрут снимается со старого и ставится на новый |
| снятие маршрута и обновление потока в платформе не были упорядочены | прежний маршрут снимается **до** того, как провайдер узнает новый поток (иначе исполнитель снял бы маршрут по новому адресу) |
| «до/после» могло смешать два разных сервера | числа «до» помечаются как относящиеся к прежнему серверу: выигрыш за сессию не заявляется, базовая линия для контроля деградации набирается заново |

Честно про `PingForge.Routing`: `RouteScorer`, `RouteSelector`, `FailoverController` покрыты

Что осталось (не выдаётся за сделанное):
- маршрут ставится на один адрес сервера (`/32`). Для Minecraft-серверов за прокси/CDN это норма
  (адрес один), но при переезде прокси на другой адрес маршрут перестраивается только по правилу
  «прежний адрес исчез» из §3.1;
- Minecraft по TCP означает, что «пинг» в игре — это TCP-обмен, а не ICMP; программа и меряет живой
  TCP-поток, поэтому числа сопоставимы с тем, что видит игра, но сравнивать их с `ping` из консоли нельзя;
- сервер на нестандартном порту (SRV-запись на 30000 и т.п.) сам по себе игрой не назовётся: угадывать
  по общему имени `javaw.exe` программа не станет. Выход есть и он честный: человек добавляет `javaw.exe`
  как **свою** игру («Мои игры» → «Добавить игру»), встроенная запись общего процесса заменяется
  (`GameProcessCatalog.WithCustomGames`), проверка порта снимается, и оптимизация работает на любом порту.
  Удаление своей записи возвращает встроенную карточку Minecraft (Java);
- живых прогонов с настоящим Minecraft/Fortnite на сборочной машине нет (игр там не ставят): проверено
  юнит-тестами детектора (`NetworkFlowTests`), каталога и полным зелёным CI.

Тесты этого шага (9 новых): Minecraft Java по 25565 (и `java.exe` как алиас), Java на чужом порту —
кандидат, а не игра, Bedrock по UDP 19132, Fortnite выбирает матч, а не голос (и на известном диапазоне,
и на неизвестном высоком порту — там голос получает штраф `VoicePorts`), IPv6-поток виден и объяснён,
поиск игр на диске не ищет общий `javaw.exe` (найденный чужой Java-процесс нельзя выдавать за игру),
своя игра поверх общего процесса заменяет встроенную запись и возвращает её при удалении, а встроенную
игру с однозначным именем своя запись не перекрывает.

## 3.3 Живая проверка игровых потоков на Windows (G1) и порты разных игр

Настоящую игру на сборочную машину не поставить: нужны лицензия, аккаунт и GPU, а раннер ещё и
без видеокарты. Поэтому «запустить игру онлайн» проверяется ближайшим честным способом — **живым
сетевым потоком процесса с именем клиента игры**:

| Что делает скрипт `tools/games-live-checks.ps1` | Что это доказывает |
|---|---|
| копирует `powershell.exe` как `javaw.exe` и держит TCP-соединение к публичному адресу на порт 25565 | служба видит настоящую строку таблицы соединений Windows, настоящее имя процесса и называет «Minecraft (Java)» с этим адресом |
| то же имя `javaw.exe`, но порт 2222 (не Minecraft) | Minecraft **не** называется: угадывания по одному имени файла нет |
| копирует `powershell.exe` как `FortniteClient-Win64-Shipping.exe` и шлёт UDP на 1.1.1.1:9005 | трассировка UDP (`EtwUdpPeerListener`) действительно находит собеседника, и поток матча не путается с голосом |
| после каждой проверки — `realtime-stop` | то, что служба подняла (QoS DSCP), снимается; шаг герметичен |
| если наружу на 25565 не пускают | печатается «пропущено» с причиной, а не зелёный результат |

Служба при этом идёт своим обычным путём (`realtime-start` → поиск потока → замер «до» → действия),
то есть проверяется весь продуктовый маршрут, а не отдельная функция. Ограничение названо прямо:
игра не установлена, проверяется распознавание потока и поведение службы, а не игровой клиент.

Заодно расширены порты **разных** игр (16 записей каталога): VALORANT 7000–8000 и 8180–8181,
Apex 37000–40115, Rocket League 7000–9000 и 27000–27031, PUBG 7086–7995 и 12070–12460,
CS2/Dota 2 27015–27050, Rust 28015–28017, Rainbow Six 6015, GTA Online 6672 и 61455–61458,
FiveM 30120, Destiny 2 3074/3097, Warframe 4950/4955, League of Legends 5000–5500,
Call of Duty 3074 и 27000–27050, Overwatch 2 1119/3724/6113/6250 (у Blizzard это же и порты голоса,
поэтому они заданы как порты игры, а не как «голос»). Источники — публичные таблицы портов игр
(portforward.com, EA/Blizzard-справки, community-логи Apex `37x15–40x15`).

Тесты этого шага (3 новых): «детектор узнаёт каждую игру каталога по её порту» (18 игр, сторож на
число проверенных), «порты игр не пересекаются с веб- и служебными» (весь каталог), «поток матча
выигрывает у голосового чата» для пяти игр с диапазонами.

### Что дал живой прогон `44023995101` (первый, где G1 вообще запускался)

```
G Minecraft OK: Minecraft (Java) 68.86.180.35:25565
G «не угадывает» OK: игра «Игра не определена» (ожидалось: не Minecraft)
G Fortnite OK: Fortnite 1.1.1.1:9005
G OK: служба называет игру по живому потоку и не угадывает её по одному имени процесса
```

То есть на настоящей Windows: строка таблицы соединений от `javaw.exe` опознана как Minecraft (Java)
с адресом `68.86.180.35` (это portquiz.net, который принимает TCP на любой порт), тот же процесс с
портом 2222 игрой **не** назван, а UDP-поток от `FortniteClient-Win64-Shipping.exe` найден трассировкой
стека и назван Fortnite с портом 9005 (1.1.1.1 — публичный адрес, ответ не нужен).

Честно про то же прогон: `realtime-start` вернул `exit 2` — служба **нашла** игру, но замер «до» на
раннере не состоялся (у сборочной машины закрыты ICMP и прямой доступ к чужим портам, а провайдер
живого потока в службе не подключён). G1 проверяет именно называние игры и адреса, а не пинг; причина
отказа теперь и в аннотации, и в тексте службы: «Живой поток игры Minecraft (Java) (68.86.180.35:25565)
не измеряется…» — раньше отказ не называл ни игру, ни адрес, и проверить его было нечем.

## 3.4 Внешний вид: тёмная тема 0.3 и снимки, по которым видно вёрстку

Интерфейс был рабочим, но плоским: одинаковые панели, системные выпадающие списки и полосы
прокрутки, заголовки одного кегля. Переделано только оформление — ни одна привязка, ни одно имя
элемента и ни один текст, которые ищут проверки, не тронуты.

| Что | Где | Что именно |
|---|---|---|
| Палитра и токены | `App.xaml` | Фон `#070B14`, панель с градиентом `#152034 → #111A2A`, «утопленная» панель `#0B1220`, акценты прежние (зелёный, циан), добавлены фиолетовый, предупреждение и опасность. Шрифт интерфейса — Segoe UI, числа — Consolas |
| Глубина | `App.xaml` (`Card`) | Карточки: градиент, скругление 14, тонкая рамка и мягкая тень (16 px, 28 %). Главная карточка экрана — `HeroCard` с акцентной кромкой |
| Кнопки | `PrimaryButton`, `GhostButton` | Градиент и свечение при наведении, нажатие, кольцо фокуса с клавиатуры, отдельное состояние «недоступно» |
| Разделы | `NavButton` | Выбранный раздел — светлая плашка с акцентной кромкой слева и полужирным текстом |
| Показатели | `StatTile`, `StatValue`, `StatLabel` | Плитка с «утопленным» фоном, число моноширинным шрифтом, подпись капсом |
| Списки и таблицы | `ListRow`, `SunkenPanel` | Тонкие линии-разделители, вложенные панели без тени |
| Вкладки, чипы, тумблеры | `Style TargetType="TabItem"`, `Chip`, `ToggleSwitch` | Вкладки журнала и пресеты твиков — пилюли; тумблер вкл/выкл с кольцом фокуса |
| Ввод | `TextBox`, `ComboBox`, `ComboBoxItem` | Тёмные поля и тёмный выпадающий список: системный белый список на тёмной панели читался как обломок светлой темы |
| Прокрутка | `ScrollBar` | Тонкая полоса 10 px без стрелок: колесо и перетаскивание работают как раньше |
| Окно | `MainWindow.xaml` | Шапка с эмблемой и подписью, свечения фона, колонка разделов с заголовком «РАЗДЕЛЫ», содержимое ограничено 1040 px и центрировано, подвал с честной плашкой |
| Заставка | `SplashWindow.xaml` | Градиентная кромка, крупнее эмблема, полоса-градиент вместо системного ProgressBar |

**Чем проверяется.** Вёрстку нельзя проверить юнит-тестом, поэтому проверка — снимки живой Windows:
`ui-walkthrough.yml` запускает программу, проходит мастер и разделы и кладёт PNG в артефакты.
По дороге нашлась ошибка самой проверки: снимок делался `CopyFromScreen` по прямоугольнику окна, а
экран сборочной машины меньше окна 1180×820 — правый край снимка обрезался, и по нему нельзя было
судить о вёрстке. Теперь `Save-Window` делает снимок через `PrintWindow` с `PW_RENDERFULLCONTENT`
(окно рисуется в память, размер экрана не важен), процесс объявлен DPI-осведомлённым, а в журнал
печатается размер экрана. Если `PrintWindow` не сработал — честный откат на снимок с экрана.

**Что проверяется машинно, а не на глаз.**

- `UiThemeTests` (6 тестов): каждый `{StaticResource …}` в окне и разделах действительно определён
  (опечатка в ключе — это падение окна у человека, а не предупреждение сборки); у тёмной темы есть
  свои шаблоны для `ScrollBar`, `ComboBox`, `TabItem`, `TextBox`, `ToolTip`; видимый фокус с клавиатуры
  задан не меньше четырёх раз; палитра и шрифты заданы ключами, а не цветами по месту; главное
  действие выделено `HeroCard`; снимок живой проверки снимается `PrintWindow`, а не с экрана —
  и в `build.yml`, и в `ui-walkthrough.ps1`.
- Шаг «Снимок окна — что на нём» в `build.yml` считает по снимку размер, среднюю яркость и долю
  тёмных пикселей и пишет их в аннотацию: `Снимок окна 1180x820: средняя яркость 14%, тёмных 86%…`.
  Одноцветный снимок — ошибка (окно не отрисовалось), светлый — предупреждение (тема не применилась),
  ширина меньше окна — предупреждение (край обрезан). Это проверка доказательства: артефакты
  лежат на чужом хранилище и из песочницы не скачиваются.

**Честное ограничение.** Локальной Windows у помощника нет: сборка, снимки и поведение окна видны
только по прогону CI. Поэтому в этом разделе описан макет, а не «как красиво на вкус автора»:
что именно получилось — видно на снимках артефакта `walkthrough-windows`.

## 4. Как собрать и проверить

Сборка, тесты и живая проверка идут в GitHub Actions на каждый push (прогон называется
«Сборка, тесты и готовые .exe»): сборка с 0 предупреждений → 866 тестов → витрины → компактные и
автономные сборки → живой запуск окна на сборочной Windows (`--self-check` + снимок окна) →
установщик NSIS и его тихая проверка с живым разговором со службой.

**Обратная связь из песочницы.** Логи прогонов (`gh run view --log`) из песочницы не скачиваются
(`results-receiver.actions.githubusercontent.com` → `EOF`), артефакты (`gh run download`) недоступны.
Работает API — в том числе единственный канал текста ошибок, **аннотации**:

```bash
# статус и шаги
HOME=/home/user gh run view <run-id> --repo Doxaiz/Custom-Tweak-By-Doxaiz --json jobs \
  --jq '[.jobs[0].steps[] | "\(.conclusion // "идёт") \(.name)"] | .[]'
# ошибки компилятора и предупреждения — аннотации (единственный канал текста ошибок!)
HOME=/home/user gh api repos/Doxaiz/Custom-Tweak-By-Doxaiz/check-runs/<job-id>/annotations \
  --jq '.[] | "\(.annotation_level) \(.path):\(.start_line) — \(.message)"'
```

Локально в песочнице .NET SDK недоступен (см. §5) — собирать и тестировать можно только через CI.

## 5. Подводные камни песочницы (уже проверены на опыте)

- **`.git/config` не попадает в снимок воркспейса.** После восстановления окружения `origin` и
  `user.name` пропадают, а `HEAD` может откатиться на старый коммит. Лечение:
  `git remote add origin https://github.com/Doxaiz/Custom-Tweak-By-Doxaiz.git`,
  `git fetch origin main`, `git reset --mixed origin/main` — файлы не меняются, история восстанавливается.
- **`.NET SDK не поставить.** Адреса dotnet CDN и `objects.githubusercontent.com` из песочницы
  не проходят, pypi-аналога нет. Собирать можно только в CI; «проверить локально» означает
  «дождаться прогона и прочитать аннотации».
- **`edit_file` не умеет C#-литералы с обратными слэшами** (`@"C:\Games\cs2.exe"`): «context not
  found». Править такие места через `python3` и `str.replace` с проверкой `count == 1`.
- **`git stash pop` путает правки.** Рабочие правки и уже закоммиченные переименования в одном файле
  сливаются в конфликт, а восстановленный stash может откатить чинку. Правило: stash — только когда
  в рабочем дереве нет правок того же файла, и сразу после pop сверять `git diff`.
- **`git commit -a <пути>` не работает** (`fatal: paths ... with -a does not make sense`): коммитить
  точечно без `-a`.
- **Тесты не ищут исходники обходом вверх.** `dotnet test` идёт с `--artifacts-path` вне папки
  решения — файлы для текстовых проверок копируются в вывод теста (`PingForge.Tests.csproj`,
  `checked-*`). Ссылки `Link` — без разделителей-слэшей: на Linux MSBuild понимает `checked\file`
  как одно имя.
- **xUnit1031** — в тестах нельзя `Task.WaitAll`/`.Result`: только `async Task` и `await Task.WhenAll`.
- `bin/` и `obj/` раздувают снимок: перед паузой чистить
  `find . -type d \( -name bin -o -name obj \) -prune -exec rm -rf {} +`.
- `python3 tools/render_ui_preview.py` **без аргумента** падает: нужен `docs/catalog.json`.
- PowerShell: `.ps1` должен иметь **ровно одну** метку UTF-8 BOM; inline `run:` в YAML — только ASCII.

## 6. Правила, которые нельзя нарушать

- Программа при запуске **ничего не меняет**; изменения — только по нажатию кнопки и с подтверждением.
- Любое изменение — через снапшот и точку восстановления, с честным откатом.
- Запрещено: инжект DLL и доступ к памяти игры, отключение анти-читов/Defender/брандмауэра/обновлений/UAC/
  подписи драйверов, подмена MAC/IP, телеметрия, обещания «пинг 0».
- Выигрыш заявляется **только измеренный**: «пинг снизился с X до Y» — факт из замера, иначе «заметного
  выигрыша нет» или «стало хуже, причина в маршруте».
- Имя приложения — «Custom Tweak By Doxaiz»; пространства имён, пути и имя репозитория не переименовывать.
- Интерфейс и структуру по BoosterX не переделывать; шесть разделов, мастер первого запуска, лаунчер «Открыть».
- Ничего не выдумывать: «не измерено» не становится нулём; неизвестный процесс — «кандидат», а не игра.
- В каталоге маршрутизации — только бесплатные и безопасные методы; без платных VPN/ускорителей и
  выдуманных «серверов PingForge».
