# Каналы службы: кто и что может

Служба «Custom Tweak By Doxaiz» слушает **два** именованных канала. Разделение нарочное: канал,
который меняет настройки Windows, не должен быть доступен каждому залогиненному пользователю.

## Основной канал — `\\.\pipe\PingForge.Engine.v1`

| Кому | Права | Почему |
|---|---|---|
| Служба (LocalSystem, `S-1-5-18`) | полный доступ | создаёт и обслуживает канал |
| Администраторы (`S-1-5-32-544`) | полный доступ | установка, починка сети, обслуживание |

Команды — все четырнадцать, включая меняющие Windows (`apply-preset`, `apply-tweaks`, `rollback`,
`repair-network`, `realtime-start`, `perf-profile`, `route-measure`).

Подключение к каналу **не даёт** права менять систему: перед каждой командой, которая меняет
настройки, служба проверяет права того, кто подключился, **в его собственном процессе** (а не свои —
свои у неё от LocalSystem есть всегда). Отказ пишется в журнал службы с именем и SID клиента.

## Канал только для чтения — `\\.\pipe\PingForge.Engine.ReadOnly.v1`

| Кому | Права | Почему |
|---|---|---|
| Служба (LocalSystem) | полный доступ | обслуживает канал |
| Администраторы | чтение и команды | смотреть можно из любого канала |
| Интерактивный вход (`S-1-5-4`) | байты в обе стороны, **команды — только чтение** | окно и значок в трее работают от обычного пользователя; соединение открывается сразу на запрос и ответ (одного чтения не хватает даже на подключение — проверено живым pfcheck), а набор команд ограничивает диспетчер, а не ACL |

Обычное окно программы (запущенное без прав администратора) подключается именно сюда и может
просматривать состояние, читать журнал и останавливать свои изменения. Кнопки изменений при этом
честно объясняют: «запустите программу от имени администратора».

### Команды канала только для чтения

Список ровно такой, как в коде (`EngineCommandCatalog.ReadOnlyChannelKinds`) — тест
`Список_команд_канала_чтения_совпадает_с_этим_документом` сверяет этот блок с кодом, чтобы документ
не разошёлся с реальностью:

```
ping
capabilities
status
journal-tail
system-state
route-discover
realtime-stop
uninstall-check
sessions
```

Всё остальное, включая `perf-profile` и `route-measure`, канал чтения **не выполняет даже для
администратора**: изменения идут только через основной канал, где работают все проверки прав.
`realtime-stop` оставлен намеренно — он ничего не настраивает, а снимает СВОИ изменения, и
«убрать за собой» должно работать без прав. `route-discover` — тоже намеренно: это только чтение
таблицы маршрутов и списка адаптеров, менять там нечего. `uninstall-check` — только чтение журнала
и снапшотов: скрипт удаления спрашивает службу до того, как что-то удалить, и спрашивать — не менять.
`sessions` — история замеров: окно читает её и без прав, а очистка (`sessions-clear`) — меняющая
команда и доступна только на основном канале.

## Как служба узнаёт, кто подключился (C7)

Личность клиента определяется по процессу самого клиента: сервер канала вызывает
`GetNamedPipeClientProcessId` (именно клиент, не сервер — обратная функция вернула бы PID
самой службы), открывает токен этого процесса правом `TOKEN_QUERY (0x0008)` и читает имя,
SID и принадлежность к администраторам из этого токена. Олицетворение (`RunAsClient`) для
этого не используется: клиент с уровнем Anonymous через него не виден.

Имя и SID клиента пишутся в журнал службы при каждом подключении и при каждом отказе по
правам. Ответ `ping` называет подключившегося полями `clientName`, `clientSid` и
`clientIsAdmin` — по ним живая проверка на раннере (`PingForge.EngineSmoke --expect-identity`)
сличает то, что видит служба, с токеном самого проверяющего процесса. Если личность прочитать
не удалось, служба считает, что прав у клиента нет.

## Чья ветка пользователя меняется

Служба работает от LocalSystem, поэтому её собственный `HKCU` — это профиль системы. Настройка,
записанная туда, выглядела бы применённой для проверки и невидимой для человека. Поэтому SID клиента
из C7 едет дальше, в контекст команды: настройки ветки пользователя читаются и пишутся как
`HKEY_USERS\<SID>` — от имени того, кто попросил. Если SID нет и активный сеанс не определился,
настройка не применяется: интерфейс показывает отказ с причиной, а не зелёную галочку в чужом профиле.
Машинные настройки (`HKLM`) от профиля не зависят.

## Кому не разрешено никогда

Оба канала закрыты для `Everyone` (`S-1-1-0`), `ANONYMOUS LOGON` (`S-1-5-7`), `Guests`
(`S-1-5-32-546`) и входа по сети (`S-1-5-2`, отдельное запрещающее правило). Наследование прав
от канала отключено: чужие правила «от родительской папки» в него не попадают. Если в таблицу прав
попадёт запрещённый идентификатор, канал **не открывается вовсе** — с объяснением в журнале службы.

## Как это проверяется

- таблицы прав и запрещённые SID — `ServiceSecurityTests`;
- запрет меняющих команд в канале чтения (даже для администратора) — `ReadOnlyChannelTests`;
- проверка клиента по токену процесса и отказы с объяснением — `ServiceDispatcherTests`;
- личность клиента из его процесса, а не из литерала — `EnginePeerIdentityTests`;
- сторож инспектора канала (функция и право на токен) — `PipeClientInspectorGuardTests`;
- живая личность, отказ без прав и применение с откатом на раннере — `tools/c7-live-checks.ps1`
  и флаги `--expect-identity` / `--try-apply` / `--apply-and-rollback` / `--apply-hold` у `PingForge.EngineSmoke`;
- ветка пользователя: значения применяются через `HKEY_USERS\<SID>`, а сторонний процесс читает их
  из своей учётной записи — `tools/c7-live-checks.ps1` (шаг «применение с проверкой значений»);
- сам файл `PipeAclFactory.cs` и его защитная проверка — `AppManifestAndSecurityGuardTests`.
