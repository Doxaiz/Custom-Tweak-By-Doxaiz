# Custom Tweak By Doxaiz

**PingForge** — программа для Windows 10/11: честная оптимизация игрового соединения. Маршрут до игрового
сервера, приоритет пакетов игры, твики сетевого стека Windows, замеры «до и после» и безопасный откат.
Без инжекта в игры, без доступа к памяти игр, без выключения защиты Windows.

`PingForge` — рабочее (внутреннее) имя решения. Продуктовое имя в интерфейсе — **Custom Tweak By Doxaiz**
(см. `docs/NAMING.md`).

## Установка для пользователя

**Обычный случай — установщик.** Скачайте `CustomTweakByDoxaiz-Setup-0.3.0.exe` со страницы
[**Releases**](https://github.com/Doxaiz/Custom-Tweak-By-Doxaiz/releases/latest) (или возьмите готовые
файлы из артефактов последней сборки во вкладке **Actions**) и запустите: он положит программу в
`C:\Program Files\Custom Tweak By Doxaiz`, зарегистрирует и запустит службу, создаст ярлыки и появится
в «Программах и компонентах». Ничего доустанавливать не нужно. Установщик не подписан сертификатом EV,
поэтому SmartScreen может спросить подтверждение — «Подробнее» → «Выполнить в любом случае».

Если установщик не нужен — есть три других способа:

1. `CustomTweakByDoxaiz-0.3.0.exe` — программа одним файлом, без установки. Служба лежит рядом отдельным
   файлом `CustomTweakByDoxaiz.Service-0.3.0.exe`: положите его рядом с программой и запустите
   `install-service.ps1` от имени администратора — иначе менять настройки нечем.
2. `CustomTweakByDoxaiz-portable-win-x64.zip` — автономная сборка архивом: распаковать целиком и запустить
   `install-service.ps1` **от имени администратора**.
3. `CustomTweakByDoxaiz-compact-win-x64.zip` — то же, но нужен .NET 10 Desktop Runtime.

Если служба не зарегистрировалась, установщик скажет об этом и оставит рядом с программой журнал
`install-service.log` — по нему видно, что именно не получилось.

После установки откройте программу и нажмите «Оптимизировать соединение»: до этого нажатия программа
ничего не меняет.

Подробно — [`docs/УСТАНОВКА.md`](docs/УСТАНОВКА.md).

## Сборка своими руками

```bash
dotnet build PingForge.slnx
dotnet test  PingForge.slnx
# готовые .exe (программа + служба)
dotnet publish src/PingForge.App/PingForge.App.csproj -c Release -r win-x64 --self-contained false -o dist
dotnet publish src/PingForge.Service.Host/PingForge.Service.Host.csproj -c Release -r win-x64 --self-contained false -o dist
```

Автономный вариант (без установки .NET): добавьте `--self-contained true -p:PublishSingleFile=true`.

## Что программа не делает никогда

Не влезает в игру и не трогает её память, не выключает анти-читы, не отключает Защитник Windows,
брандмауэр, обновления и UAC, не подменяет MAC/IP, не меняет настройки роутера, не обещает «пинг 0»,
не собирает телеметрию. Ни одного изменения — без подтверждения и снапшота прежних значений.

## 1. Как собрать и прогнать тесты

Сборка проверяется на чистом Linux-контейнере (.NET 10). Тяжёлые артефакты намеренно уводятся
в `/var/tmp`, чтобы рабочая папка оставалась лёгкой (≈370 КБ).

```bash
# 1) Один раз: поставить SDK в /var/tmp (в /tmp ставить НЕЛЬЗЯ — там файлы выходят битыми)
curl -sSL https://dot.net/v1/dotnet-install.sh -o /var/tmp/dotnet-install.sh
bash /var/tmp/dotnet-install.sh --channel 10.0 --install-dir /var/tmp/dn

# 2) Переменные окружения (в каждой новой оболочке)
export DOTNET_ROOT=/var/tmp/dn
export PATH=/var/tmp/dn:$PATH
export DOTNET_CLI_HOME=/var/tmp/dnhome
export NUGET_PACKAGES=/var/tmp/nuget
export DOTNET_NOLOGO=1

# 3) Сборка и тесты
cd /home/user/pingforge
dotnet build PingForge.slnx --artifacts-path /var/tmp/pf-art
dotnet test  PingForge.slnx --artifacts-path /var/tmp/pf-art
```

Последний прогон: **534 теста, 0 падений** (`Failed: 0, Passed: 534`), 134 файла C# (107 из них — код, 27 — тесты).

Полный локальный прогон — это шесть шагов, и все они зелёные: сборка (0 предупреждений, 0 ошибок) → 534 теста →
выгрузка каталога (`PingForge.CatalogDump`: 47 твиков, 0 проблем, 0 нарушений запретов) → два рендера → четыре
чекера интерфейса: рабочий документ 94/94 и 21/21, витрина 77/77 и 34/34. Последние два — в настоящем браузере
(headless Chrome); подробности в §8.0.

Проект `PingForge.Tweaks.Windows` собирается и на сборочной машине без Windows
(`<EnableWindowsTargeting>true</EnableWindowsTargeting>`) — это проверяет типы, но не поведение.

**На сборочной Windows поведение теперь проверяется по-настоящему.** После сборки сценарий собирает установщик,
тихо ставит его (`/S`), проверяет файлы, ярлык в меню «Пуск» и запись в «Программах и компонентах», ждёт
запуска службы `PingForge`, затем запускает утилиту `tools/PingForge.EngineSmoke` — она разговаривает
со службой тем же каналом, что и окно программы, и спрашивает у неё `ping`, `capabilities`, `status`,
`system-state` и `journal-tail`. Чтение состояния при этом трогает настоящий реестр и настоящий `netsh`.
После проверки установщик тихо удаляется, и сценарий убеждается, что службы, ярлыка, папки и записи в реестре
не осталось. Ничего из этого не требует человека у экрана.

> `.slnx` создан вручную: в установленном SDK нет шаблона `dotnet new sln`.

### 1.1. Грабли, которые видны только на Windows

Первая сборка на GitHub Actions упала там, где локально всё было зелёным. Причина одна: Linux прощает
то, чего не прощает Windows. Записано, чтобы не наступить второй раз.

| Что | Как проявляется на Windows | Как сделано сейчас |
|---|---|---|
| Пул соединений SQLite | Пул держит дескриптор файла и после закрытия соединения, поэтому удаление файла базы падает с «файл используется другим процессом». В тестах это уронило 7 проверок из 450. | `SqliteDatabaseInitializer.ClearFileHandles()` закрывает пул; тесты убирают за собой через `TempDatabaseFile` (он же сносит побочные `-wal`, `-shm`, `-journal`). |
| Кодировка консоли | Консоль Windows по умолчанию cp1252, и `print("Готово: …")` в python-утилитах падает с `UnicodeEncodeError` — уже **после** того, как файлы записаны. | В `tools/render_*.py` вывод переключается в UTF-8 (`sys.stdout.reconfigure`), а в workflow заданы `PYTHONUTF8` и `PYTHONIOENCODING`. |

| Канал: имя команды | Не Windows-особенность, а то, что видно **только когда обе стороны встретились**. Клиент отправлял имя команды, собранное из имени значения перечисления: `read-system-state` вместо `system-state` и `rollback-snapshot` вместо `rollback`. Служба отвечала «команда неизвестна» — то есть чтение состояния и возврат настроек не работали бы вовсе, хотя «все тесты были зелёными»: тесты службы разбирали правильные строки, тесты интерфейса — двойник канала. | Имя команды берётся из таблицы команд (одно место на обе стороны), а тест `Каждая_команда_переживает_дорогу_через_JSON_под_своим_именем` прогоняет через JSON каждое значение перечисления. Утилита `PingForge.EngineSmoke` проверяет то же самое на живой службе в CI. |

Вывод на будущее: удаление и переименование файлов, а также вывод кириллицы в консоль проверять
на Windows, а не только на Linux. А ещё: если две части системы разговаривают строками, нужен тест,
который проводит через стык **все** значения, а не одно удобное.

### 1.2. Установщик: грабли, которых не видно, пока не соберёшь его на Windows

Установщик — единственная часть, которую нельзя проверить ни на Linux, ни глазами: `makensis` в песочнице
падает на этом железе, а тихая установка проверяется только живой Windows в CI. Первый же прогон дал
девять ошибок подряд — по одной на попытку. Все они записаны здесь, потому что повторять их дорого.

| Что | Как проявляется | Как сделано сейчас |
|---|---|---|
| `SetRegView` на верхнем уровне скрипта | `makensis`: «command SetRegView not valid outside Section or Function» — сборка останавливается на первой же строке | Перенесено в `.onInit` и `un.onInit`: там это разрешено |
| `-DVERSION=$version` без кавычек | PowerShell не раскрывает переменную внутри слова `-DИМЯ=$значение` — сборка падала с `Error in script` на первом же `File` | Все аргументы `-D` берутся в кавычки |
| Пути к файлам | `makensis` ищет `File`-пути от папки **скрипта** (`installer\`), а не от корня сборки: «no files found» на существующем `dist\portable\CustomTweakByDoxaiz.exe` | В сборке передаются полные пути, а перед компиляцией печатается список файлов — если что-то не так, это видно в журнале |
| `IfSilent +2` перед `Abort` | Тихая установка отменяла **сама себя** (код возврата 2): относительный прыжок считается от следующей инструкции и попадал ровно на `Abort`. В обычном режиме незаметно — там сначала показывается вопрос | Все прыжки переведены на метки; относительных прыжков через условия в скрипте больше нет |
| Ярлыки | Создавались для вошедшего пользователя, а программа ставится в `Program Files` и записана в HKLM: у второго пользователя машины ярлыка не было бы вовсе | `SetShellVarContext all` — в установщике, в удалении и в его `.onInit` |
| Одинарные кавычки в NSIS | Переменные в них **не** раскрываются: в реестр уходил текст `$INSTDIR\Uninstall.exe` как есть, и кнопка «Удалить» в «Программах и компонентах» не работала бы | Экранированные двойные кавычки: `$\"$INSTDIR\Uninstall.exe$\"` |
| `.ps1` без метки UTF-8 | Windows PowerShell 5.1 читает такой файл как cp1252 — русские строки превращаются в мусор. `install-service.ps1` переставал регистрировать службу, причём молча | Оба скрипта записаны как UTF-8 с BOM; в `install-service.ps1` описание службы передаётся только если версия PowerShell его умеет, а отказы `New-Service` и `Start-Service` печатают причину |
| `nsExec` глотает вывод | Установка «прошла», а службы нет — и ни одной строки, чтобы понять почему | Вывод установки и снятия службы пишется в `install-service.log` / `uninstall-service.log` рядом с программой; проверка в CI при отсутствии службы печатает журнал и повторяет регистрацию с выводом на экран |
| Шаблон имени файла | `CustomTweakByDoxaiz-*.exe` не покрывает `CustomTweakByDoxaiz.Service-0.3.0.exe` — там точка, а не дефис. Файл собирался, попадал в контрольные суммы и молча не прикладывался ни к артефактам, ни к релизу | Забираются все `*.exe` и `*.zip` из `dist` |
| Проверка, которая проверяла не то | Утилита искала в ответе службы человеческую строку «Команд: 12», а служба отдаёт машинный JSON: живая проверка валилась на исправной службе. И счётчик совпал бы, если одну команду переименовать, а другую потерять | JSON разбирается: сверяются версия протокола, имена команд (какие потерялись, какие лишние) и признак «нужны права администратора» |

Вывод на будущее: у установщика и скриптов, которые он зовёт, каждый шаг должен оставлять след —
файл журнала рядом с программой. «Прошло молча» и «не прошло» выглядят одинаково, и разница видна
только тогда, когда есть что прочитать.

### 1.3. «Запустил — и ничего не произошло»

Это самая неприятная жалоба: она не говорит ничего. Ни что случилось, ни где. Первый же живой запуск
одиночного `.exe` показал, что **окно программы вообще ни разу не запускалось ни на одной машине**:
служба проверялась на сборочной Windows, а GUI — нет, потому что «окно на Linux не запустить».
Отсюда три вывода, и все три — про то, как сделать сбой видимым.

**Что оказалось на самом деле.** Живая проверка нашла настоящую причину — и это не «что-то с Windows»:

```
NullReferenceException at MainWindow.NavChanged(...)
  ← ToggleButton.OnIsCheckedChanged ← ... ← MainWindow.InitializeComponent()
```

Первый пункт меню отмечен прямо в разметке (`IsChecked="True"`), поэтому событие «выбран раздел»
приходит **во время разбора XAML** — раньше, чем созданы страницы `PageOptimize`, `PageTweaks` и остальные
(они объявлены ниже в том же файле). Обработчик к ним обращался, получал ничто и падал. Окно не строилось,
процесс завершался: ни окна, ни ошибки, ни следа. На Linux этого не видно вообще — WPF там не запускается.

Дальше снимки окна со сборочной машины нашли ещё три ошибки, каждая из которых делала программу
непригодной, но ни одну из них не поймал бы ни один автотест:

| Что | Как проявлялось | Как сделано сейчас |
|---|---|---|
| Привязка страниц | У «Оптимизации» и «О программе» `DataContext` был привязан к `{Binding Main}`, а свойство в модели окна называется `MainScreen`. Привязка молча не срабатывала: большая кнопка стояла **без надписи**, карточки — без чисел | `{Binding MainScreen}`; самопроверка ищет в дереве окна живые надписи («Оптимизировать соединение», «Твиков в каталоге: N») и отказывает, если их нет |
| Раскладка | Показатели делили строку с кнопкой: подпись под ней растягивала колонку, и на четыре карточки оставалось по сто точек — подписи резались | Кнопка и состояние — в одной карточке, показатели — отдельной строкой; самопроверка измеряет ширину каждой карточки и отказывает, если её сжали |
| Обрезка текста | Длинные пояснения рисовались одной строкой и обрезались по краю: «Это не глобальный VPN: о». Причина — в WPF именованный стиль **отменяет** неявный, а `TextWrapping=Wrap` был только в неявном | Перенос добавлен в `Title` и `Caption`; самопроверка ищет надписи длиннее шестидесяти знаков без переноса и отказывает |
| Никакого следа о запуске | Программа не писала ни строчки, пока не показывала окно. «Упала молча», «ещё распаковывается» и «её не пустил антивирус» выглядели одинаково | `StartupLog`: журнал запуска в `%LOCALAPPDATA%\CustomTweakByDoxaiz\app-start.log`. Первая строка — с числом миллисекунд **от старта процесса**: сразу видно, сколько ушло на распаковку одиночного `.exe`. Дальше — каждая ступень старта |
| Ошибка на старте убивала процесс | Необработанное исключение в `OnStartup` = выход без единого слова. WPF-приложение без консоли ничего не печатает | `CrashGuard` ставит перехватчики (диспетчер, домен, задачи) **до** любой работы: ошибка попадает и в журнал, и в окно с текстом и путём к журналу |
| GUI не проверялся совсем | Любая ошибка разметки, которую видно только при запуске (ссылка на несуществующий ресурс — классика), доживала до пользователя | Режим `--self-check`: проходит весь старт без показа окна — каталог → модели → окно (разбор XAML, раскладка, поиск всех пяти разделов, счёт элементов) → трей → связь со службой. Сборочная Windows запускает это **на том самом одиночном `.exe`, который скачивают люди**, и на компактной сборке. В проверке установщика то же самое делается для установленной программы — плюс строка «СЛУЖБА: отвечает» как доказательство, что окно действительно разговаривает со службой |
| Сжатый одиночный `.exe` | `-p:EnableCompressionInSingleFile=true` — красивый размер файла, но при первом запуске распаковка занимает десятки секунд без единого признака жизни. На слабом диске это выглядит как «ничего не произошло» | Для одиночных `.exe` сжатие выключено: файл больше, запуск заметно быстрее. Архивы и установщик сжимаются сами — там это ничего не меняет |

Что делать человеку, у которого программа не открылась: посмотреть журнал запуска. Если **файла журнала
нет вообще** — процесс не дошёл до своей первой строки, значит его не пустила система: `Unblock-File`,
карантин антивируса или SmartScreen. Если файл есть — в нём по шагам видно, где остановилось.

### 1.4. «Нажал кнопку — и окно повисло»

Этот дефект нашла не жалоба, а снимок: прогон «проверка как человек» прошёл по пяти разделам и принёс
**семь файлов, из которых пять оказались побайтово одинаковыми**. На снимке было видно, что написано
в заголовке окна: `Custom Tweak By Doxaiz (Not Responding)`.

**Что было.** Ответ службы показывался модальным окном с флагом `MessageBoxOptions.DefaultDesktopOnly`.
Флаг ставился «на всякий случай» — чтобы сообщение было видно и из службы. На живой Windows он сделал
другое: сообщение показывалось мимо модального цикла окна, главное окно на время ответа переставало
обрабатывать сообщения Windows и получало в заголовок `(Not Responding)`. Дальше всё логично:
UI Automation не может прочитать зависшее окно (в дампе остался **один** узел вместо сотни),
настоящие клики по меню не доходят, разделы не открываются, а проверка «три тихие секунды» успевала
уйти вперёд и не видела даже самого сообщения. Пользователь увидел бы ровно то же самое: нажал — и окно
замерло на десять секунд (столько ждёт ответа служба), и только потом появилось окно с ответом.

| Что | Как было | Как стало |
|---|---|---|
| Ответ на нажатие | Модальное окно с `DefaultDesktopOnly`: окно в `(Not Responding)`, меню не работает | **Карточка прямо на экране**: заголовок, текст ответа и кнопка «Понятно». Окно остаётся живым, ответ не потеряется, пока его не прочтут |
| Диалоги подтверждения | Тот же флаг — та же ловушка перед применением твиков | Диалог принадлежит своему окну (`MessageBox.Show(owner, …)`): окно ждёт ответа, но продолжает отвечать системе |
| Проверка «как человек» | Ждала «три тихие секунды» и уходила дальше, не увидев ответ; краснела на своей же проверке `$LASTEXITCODE` | Ждёт **до 30 секунд** и признак ответа берёт по делу («не подключён» / кнопка стала «Остановить»), проверяет отзывчивость окна через `SendMessageTimeout(WM_NULL)` и падает с текстом «окно перестало отвечать», а не молча снимает одинаковые снимки |

Урок на будущее, который теперь закреплён кодом: **программа не отвечает модальным окном на нажатие**.
Ответ на действие — часть экрана. Отдельный тест `Нажатие_кнопки_не_открывает_модальных_окон_а_пишет_ответ_в_интерфейс`
держит это правило, а самопроверка `--self-check` — карточку ответа в дереве окна.

**Чем закончилось (прогоны 39002681492, 39003410307, 39019544258, 39019988106, живая Windows).** Окно открылось за 1,3 и 1,1 секунды, кнопка нажата,
ответ появился карточкой на экране — без модального окна и без `(Not Responding)`. Разделы переключились
**через UI Automation**, запасной путь «клик мышью по координатам» не понадобился ни разу: раньше Windows
вообще не отдавала дерево окна (в дампе была одна строка), теперь — 58 строк. Снимки каждого шага разные,
и на них видно: «Твики» с пресетами и карточками, «Журнал», «Настройки» с профилем потребления,
«О программе» со списком того, чего программа не делает никогда. Снимки лежат в `docs/прогон/`.

Заодно этот же снимок нашёл ещё одну неточность: раздел «О программе» писал «Прав администратора нет»,
хотя журнал той же программы писал «есть». Права окна знает сама Windows — теперь они берутся у неё,
а не ждут ответа службы (`Окно_запущенное_от_администратора_не_пишет_что_прав_нет`).

### 1.5. «Сделай открытие как в BoosterX»: мастер, игры, заставка

BoosterX встречает человека не каталогом из 47 галочек, а тремя вопросами и одной кнопкой. У нас каталог
был, а «входа» не было: программа открывалась сразу на большой кнопке, игры запускались отдельно, а
повторный двойной щелчок по значку открывал второе окно. Это три разные вещи, и все три сделаны.

| Что | Как было | Как стало |
|---|---|---|
| Первый запуск | Сразу главный экран: непонятно, с чего начать | **Мастер**: «Начать» → три вопроса (для чего компьютер, насколько мощный, что мешает) → совет с объяснением, почему именно этот набор → «Применить» или «Позже». Ничего не меняется без подтверждения, а для ответа «только работа» игровые твики не предлагаются вовсе |
| Игры | Никакого списка: игру человек запускал сам, оптимизацию включал отдельно | Раздел **«Игры»**: 20 известных игр, статус анти-чита, честное «найдена / не найдена на диске», кнопки «Открыть» и «Указать .exe». «Открыть» запускает игру и сразу просит движок начать оптимизацию; путь запоминается в настройках |
| Открытие программы | Второй запуск = второе окно и второй значок в трее; на старте секунда-две «ничего не происходит» | **Один экземпляр**: повторный запуск поднимает уже открытое окно. **Заставка** на время старта с теми же ступенями, что и в журнале запуска |
| Ответ на действие | Модальные окна, которые вешали окно (см. §1.4) | Результат — строка на странице и карточка на главном экране; модальных окон с результатом больше нет ни в одном разделе |

Совет мастера — чистая функция (`OnboardingViewModel.Recommend`), поэтому он проверяется **таблицей**,
а не «на глаз»: 5 сочетаний ответов на пресет, 3 на профиль потребления, 1 на «только работа».
Таблица в `tests/PingForge.Tests/OnboardingAndLauncherTests.cs`.

Проверка «как человек» теперь идёт и по этому пути: на живой Windows она нажимает «Начать», отвечает
на три вопроса, снимает совет, закрывает мастер кнопкой «Позже» — и отдельно проверяет «Открыть игру»
по-настоящему: запускает игру и убеждается, что процесс появился в системе.

## 4. Инварианты, которые нельзя нарушать (живой чек-лист)

- Не инжектим DLL в игры, не читаем память игр, не трогаем анти-читы.
- Не отключаем Defender, брандмауэр, обновления безопасности, UAC, подпись драйверов.
- Не подменяем MAC/IP.
- Никогда не обещаем «пинг 0» и не рисуем выигрыш, которого нет (нулевой выигрыш показывается как нулевой).
- Любое изменение — только после подтверждения пользователем и только после снапшота.
- Каждое изменение попадает в предзапись журнала (PENDING) до записи в систему; при сбое — автооткат.
- Никакой телеметрии: приложение не отправляет наружу данные о системе и пользователе.
- Релей — отдельный продукт (PingForge Relay) с серверной частью; в Lite только твики, анализ и замеры.

## 5. Анализ сети: что применяем и почему (`PingForge.Analysis`)

Здесь заканчивается цепочка «замер → решение → твик». Слой не выдумывает значения: он либо получает
измеренное число, либо честно отказывается от предложения.

| Компонент | Что делает | Честное поведение |
|---|---|---|
| `MtuAdviceProvider` | Считает MTU DF-пробами до игрового сервера | Нет сервера / нет прав на ICMP / текущий MTU не прочитан → значение не предлагается |
| `DnsAdviceProvider` | Выбирает резолвер по бенчмарку | Резолвер с признаком перехвата исключается даже «быстрый»; если перехватывают все — текущие настройки остаются |
| `SystemNetworkContextReader` | Читает адаптеры, MTU и DNS через `System.Net.NetworkInformation` | Непрочитанное попадает в `UnresolvedFields`, а не заменяется значением по умолчанию |
| `NetworkAnalyzer` | Ищет то, что мешает: активный VPN/туннель, несколько подключений, непрочитанные поля | Каждое предупреждение содержит объяснение и что с этим делать; совет без замера уходит в «пропущено» с причиной |
| `InputLatencyAdvisor` | Разбирает задержку ввода: устройства, фильтр клавиатуры, фоновая запись, очередь пакетов на карте | Предложение появляется только после чтения текущего значения; нет устройства или чтение не удалось → в «пропущено», а не «применим наугад» |
| `IPeripheralInventoryReader` / `WindowsPeripheralInventoryReader` | Список мышей и клавиатур из PnP; беспроводное устройство определяется по явному маркеру имени | Ошибка чтения ≠ «устройств нет»: неизвестное уходит в `UnresolvedFields`, а связанные твики пропускаются |

Коды предупреждений `NetworkAnalyzer`: `TUNNEL_ACTIVE`, `MULTIPLE_ACTIVE_PATHS`, `CONTEXT_INCOMPLETE`.
Коды `InputLatencyAdvisor`: `PERIPHERALS_UNKNOWN`, `WIRELESS_POINTER`, `INPUT_OVER_WIFI`, `INPUT_PATH_THROUGH_ROUTER` —
последний прямо говорит, что в роутер/модем программа не заходит, и отдаёт список ручных проверок.
Каждый отчёт заканчивается фразой, которую нельзя выкинуть: правки убирают задержки на вашей стороне,
но **пинг внутри боя они не снижают** — маршрут провайдера и скорость света от настроек Windows не зависят.

## 6. Задержка ввода: мышь, клавиатура, кадр, очередь пакетов

Задержка между движением руки и картинкой почти не связана с сетью. Поэтому раздел собран отдельно,
и в нём прямо написано, что чем твики не помогают.

| Твик | Что делает | Честная граница |
|---|---|---|
| `MOUSE_ACCEL_SPEED`, `MOUSE_ACCEL_THRESHOLD1`, `MOUSE_ACCEL_THRESHOLD2` | Обнуляют акселерацию указателя | Идут только вместе: пока хоть один параметр не 0, «повышение точности указателя» остаётся частично включённым |
| `MOUSE_SENSITIVITY_NEUTRAL` | Нейтральная скорость 6/11 | Любое другое значение — системный множитель поверх чувствительности в игре |
| `KEYBOARD_FILTERKEYS_OFF` | Выключает «фильтр ввода» клавиатуры (Flags = 126) | Фильтр отбрасывает короткие и повторные нажатия; включается сам после случайного удержания правого Shift |
| `KEYBOARD_REPEAT_DELAY_MIN` | Минимальная задержка автоповтора | В предложения анализатора **не попадает**: на игровой отклик не влияет, и это сказано прямо |
| `GAME_DVR_OFF`, `GAME_DVR_CAPTURE_OFF` | Выключают фоновую запись Xbox | Xbox Game Bar не удаляется, включается обратно в любой момент |
| `NIC_PACKET_PRIORITY_ON` | Приоритет пакетов в драйвере карты (802.1p/DSCP) | Работает только если роутер уважает приоритет; на виртуальном адаптере не предлагается |

Что советник задержки ввода делает обязательно: читает список устройств ввода (нет мыши — нет твиков акселерации),
сравнивает текущее значение с рекомендуемым (совпало → «уже настроено»), и заканчивает отчёт честной строкой —
правки убирают задержку на вашей стороне, но скорость интернета и задержку внутри игрового сервера не меняют.

Чего в предложениях не будет: задержки радиоканала беспроводной мыши (обычно 125 Гц ≈ 8 мс правками реестра
не лечится), настроек роутера или модема — в устройство программа не заходит, вместо этого печатается список
ручных проверок (приоритет трафика, энергосбережение Wi-Fi, режим моста).

## 7. Кнопка «Оптимизировать соединение» (живой режим)

Сценарий пользователя: игра уже запущена (например, Fortnite), пинг 120 мс — нажимаем кнопку,
оптимизация включается на ходу и держит пинг в реальном времени; чем ниже, тем лучше.

Как это устроено (`src/PingForge.Orchestration/Realtime`):

| Шаг | Что происходит | Код |
|---|---|---|
| 1 | Поиск запущенной игры и её живого сетевого потока | `IGameFlowWatcher` |
| 2 | Замер «до»: 3 окна по 12 проб, медиана окон | `IRealtimeMeasurementSource` |
| 3 | План действий: маршрут только для адреса игрового сервера + политика QoS (DSCP 46) | `OptimizationActionPlanner` |
| 4 | Применение с проверкой каждого шага, отказ виден в отчёте | `IOptimizationActionRunner` |
| 5 | Контроль каждые 2 с: просадка → переключение пути, восстановление → возврат | `RealtimeOptimizer.TickOnceAsync` |
| 6 | Остановка: снятие в обратном порядке + честный итог «до/после» | `RealtimeOptimizer.StopAsync` |

Что важнее всего в этом режиме:

- **Твики этой кнопкой не применяются.** Твики — отдельная кнопка со снапшотом и точкой восстановления.
  Смешивать «понизить пинг сейчас» и «переписать настройки стека» в одном действии нельзя: у них разная цена ошибки.
- **Ноль обещаний без замера.** Итог считается как разница медиан живого пинга и сопровождается физическим
  пределом пути (минимальный RTT): ниже него маршрут опуститься не может, и это видно пользователю.
- **Нет выигрыша — так и написано.** Проверено тестами: «Заметного выигрыша нет», «Стало хуже… тут помог бы только релей».
- **Без прав администратора** кнопка объясняет причину и работает в режиме «только замеры».
- **Игры с ядерным анти-читом** получают только маршрут и QoS: фильтр пакетов не поднимается.

Честно про 120 → 80: настройки Windows на готовом маршруте дают единицы миллисекунд. Десятки даёт смена
пути — либо альтернативный шлюз (если у вас два провайдера), либо релейный POP (PingForge Relay, отдельный
продукт: нужен сервер). Если путь физически длинный, приложение покажет предел и не будет делать вид, что стало лучше.

### 8.0. Почему переключение разделов сделано на радиокнопках

Сначала разделы переключались ссылками-якорями (`:target`), и это оказалось хрупким: в предпросмотре
пользователя страница открывается внутри изолированной рамки, где якоря не меняют адрес, и разделы просто
не открывались («сайт не робит»). Промежуточный вариант с `:has()` отпадал по другой причине — он не работает
в браузерах без этого селектора.

Текущая схема — скрытые радиокнопки и `<label>`:

| Что | Как устроено |
|---|---|
| Разделы | 7 скрытых `input.state[type=radio]` стоят **выше** `.body`, у каждого пункта меню — свой `<label for=…>` |
| Показ | `#nav-tweaks:checked ~ .body #page-tweaks{display:block}` — обычный селектор-сиблинг, работает везде |
| Подсветка пункта | `#nav-tweaks:checked ~ .body nav.side label[for="nav-tweaks"]` |
| Пресеты и массовый выбор | те же радиокнопки (`ps-low`, `ps-speed`, `ps-fps`, `sel-rec`, `sel-all`, `sel-none`): пресет подсвечивает состав и приглушает остальное, режим выбора меняет вид всех ползунков |
| JavaScript | по-прежнему ни одной строки — страница читается и работает с полностью отключёнными скриптами |

Важная деталь реализации: радиокнопки обязаны стоять до `.body`, иначе `~` до них не дотягивается. Именно
поэтому разметка собирается генератором, а не правится руками.

Проверяется это в двух местах, потому что одного недостаточно:

- `check_app_site.js` (jsdom) — структура: связка «метка → радиокнопка», наличие правила показа для каждого
  раздела, позиция радиокнопки относительно `.body`, текстовые правила. jsdom **не** считает CSS-каскад с
  селекторами-сиблингами, поэтому по `display` там судить нельзя — это ограничение инструмента, а не баг;
- `browser_check_site.js` (headless Chrome, витрина — 34 проверки, рабочий документ — 21) — поведение: кликаем по каждому из 7 пунктов меню и
  убеждаемся, что на странице виден ровно один нужный раздел и пункт подсвечен; проверяем состав пресетов
  (19 / 5 / 23 приглушённых), переключение всех трёх режимов массового выбора по вычисленным стилям ползунков,
  раскрытие «Подробнее», отсутствие `<script>` и отсутствие горизонтальной прокрутки на экране 420 px.
  Скриншоты каждого раздела складываются в `/var/tmp/shots`.
  Для рабочего документа проверяется другое, но не менее важное: без скриптов обязаны быть видны **все** разделы
  (страница обязана читаться целиком), а с ними — каждый пункт меню отмечается выбранным, открывает хотя бы один
  раздел, разделы между пунктами не повторяются и все разделы достижимы из меню. Именно этот прогон показал, что
  один пункт меню показывает две части раздела («Сеть и маршрут» — маршрут и анализ) — проверку переписали
  под настоящее поведение, а не под ожидание.

Именно этот браузерный прогон нашёл настоящий баг: классы карточек собирались склейкой (`in-low` + `in-fps`
давало `in-lowin-fps`), из-за чего подсветка состава пресета не срабатывала. Тест в jsdom этого не видел,
потому что проверял наличие класса, а не его работу.

## 8.1. Рабочий документ интерфейса (подробный)

## 8.5. График сети: какие показатели обязательны (`PingForge.Analysis.Charting`)

График — это не украшение, а способ показать «до/после» честно. Поэтому список показателей в коде закрытый
(`NetworkChart.RequiredIndicators`, 11 штук), и по каждому известно, зачем он там:

| Показатель | Единица | Зачем в обязательном списке |
|---|---|---|
| Скорость приёма / отдачи | Мбит/с | доказать, что оптимизация не отняла пропускную способность: отдача нужна голосовому чату и античиту |
| Задержка: минимум / средняя / 95-й процентиль | мс | среднее показывает обычный пинг, p95 — «плохие» 5 % моментов, из-за которых ощущаются рывки |
| Джиттер (MAD) | мс | разброс задержки, устойчивый к одиночным скачкам: главная причина плавающего отклика |
| Потери пакетов | % | даже полпроцента ощущаются как телепорты |
| Повторы TCP | на 1000 пакетов | повторная отправка проходит путь дважды |
| Задержка под нагрузкой | мс | показывает буферблоат: если закачка задирает пинг, виноват буфер, а не провайдер |
| Время ответа DNS | мс | вход в лобби и поиск матча (на бой не влияет — так и написано) |
| MTU пути | байт | не усредняется: важно последнее подтверждённое значение, иначе фрагментация вернётся незаметно |

Правила честности, которые проверяются тестами:

1. **Нет измерения — нет нуля.** Пропущенный замер остаётся разрывом с подписью «измерить не удалось»;
   ноль на графике выглядел бы как идеальный результат.
2. **Среднее считается только по измеренным точкам** — редкие провалы видно, а не «размазано».
3. **MTU — последнее подтверждённое значение**, а не среднее по окну.
4. Окно наблюдения и число проб подписываются рядом с цифрами: без этого любые числа ничего не значат.

## 8.6. Почему «бесплатных способов» именно четыре (`GameRouteCatalog`)

Раньше тексты обещали «пять бесплатных и безопасных способов», а в данных бесплатных было четыре:
второй канал — это отдельный тариф провайдеру, то есть не бесплатно. Это была не опечатка, а расхождение
прозы с данными, и её нашли автотесты (первый же прогон `RouteCatalogTests` упал с «ожидалось 5, а их 4»).

Исправлено так, чтобы расхождение не могло вернуться:

- бесплатность описана в коде одним списком (`FreePathKindsRu`), а число и текст оговорки считаются из него
  (`FreePathCount`, `HonestNoteRu`, `DescribeSummaryRu`) — проза физически не может разойтись с данными;
- названия для фразы вынесены отдельно (`FreePathProseRu`): автоматическое приведение к нижнему регистру
  давало «ipv6» и «wi-fi», а так в интерфейсе стоит нормальное «IPv6, если провайдер его раздаёт»;
- тесты проверяют обе стороны: нет способа с ценой «0 ₽», который не помечен бесплатным, и нет платного
  способа с ценой «0 ₽»; в оговорке обязательно есть «ровно четыре», каждый бесплатный способ назван,
  а про второй канал сказано «не бесплатно»;
- в макете число бесплатных берётся из данных выгрузки, а не написано руками, и чекер макета это проверяет.

## 8.7. Вердикт «стоит включать или нет» — это часть каталога (`TweakVerdict`)

Требование было прямым: у твиков должно быть написано, стоит ли их включать. Сделано так, чтобы это было
не подписью, нарисованной в интерфейсе, а данными:

| Что | Как решается |
|---|---|
| Короткий вердикт | `включать: да` / `по желанию` / `осторожно` / `не советуем` — четыре формулировки в одном месте |
| Плашка каталога | те же четыре решения словами каталога: «Рекомендую для игр», «По желанию», «С осторожностью», «Не рекомендую» |
| Причина | одна строка, которую видно под ползунком («Рекомендуем: для игр это работает и не вредит») |
| Состояние по умолчанию | включено **только** «включать: да» (23 твика из 47); «по желанию», «осторожно» и «не советуем» выключены, и в карточке написано, почему |
| Легенда в интерфейсе | собирается из `TweakVerdict.Legend`, поэтому интерфейс не может придумать свою формулировку |

Тесты проверяют обе стороны: у каждого из 47 твиков есть вердикт и причина; рекомендованных ровно 23 и именно
они включены по умолчанию; «не советуем» (3 штуки) выключены и не попадают в авто-пресеты; названия плашек и
коротких вердиктов не дублируют друг друга (в карточке стоит один вердикт, а не два разных названия одного решения).

Движок живого режима (поиск игры → замер «до» → действия → контроль каждые 2 с → честный итог) отдельной строкой

по весам: `Σ(вес × готово) / Σ(весов)`. Рост к прошлой оценке (59 %, затем 63 %, затем 67 %, затем 73 %) — сначала за счёт каталога на 47 твиков
с подкатегориями и разными пресетами, моделей трея и экономного профиля, справочника маршрутов и графика сети,
потом за счёт службы, потом за счёт интерфейса, а в этом раунде — за счёт чтения состояния Windows:
читатель собран, покрыт 43 тестами и подключён к службе двенадцатой командой `system-state`,
а теперь ещё и проверяется на живой Windows вместе с установщиком.

История цифры: раньше веса строк сходились не к 100, а к 108 — это завышало результат примерно на 3 пункта.
Арифметику исправили (её проверяет `assert` в генераторе макета: сумма весов обязана быть ровно 100),
поэтому промежуточная оценка 59 % была ниже, а не «падением» проекта. Сейчас веса снова сходятся к 100 и
считаются нормированно.

### 9.1. Сколько работы осталось — по строкам

## 10. Что дальше (очередь работ)

1. **Сделано в раунде «до идеала»:** каталог вырос до 47 твиков с подкатегориями «пинг / скорость / кадры /
   ввод / система» и кнопками массового выбора; пресеты перестали быть одинаковыми (19 / 5 / 23, набор
   собирается правилом и проверяется тестом); появились модели трея и экономного профиля потребления
   (`PerfProfile`, бюджет ресурсов, меню трёх состояний, честные подсказки); справочник маршрутов на 22 игры
   с 5 бесплатными DNS и 8 способами сократить путь; график сети с 11 обязательными показателями
   (`PingForge.Analysis.Charting`); в макете — меню из трёх групп, мини-оглавления, «что в этой версии»,
   ползунки в карточках твиков и кнопка «Поддержать автора». Добавлены автотесты на всё это:
   `RouteCatalogTests` (18 проверок справочника) и `TrayAndResourceTests` (22 проверки трея и бюджета
   ресурсов) — именно они поймали расхождение «пять/четыре» в числе бесплатных способов.
2. **`PingForge.Network` — сделано ядро слоя:** каталог известных игр (20 игр, у каждой статус анти-чита),
   детектор игровых потоков поверх таблицы соединений, маршрутные действия (`route` с проверкой и откатом),
   политика QoS (DSCP 46) через `IRegistryPort` — 65 автотестов, включая правило «для ядерных анти-читов
   фильтр не поднимается». Windows-часть (`PingForge.Network.Windows`): чтение таблицы соединений через
   GetExtendedTcp/UdpTable, имена процессов через QueryFullProcessImageName, сборка платформы — типы проверены
   сборкой. **Осталось здесь:** трассировка ETW для адресов UDP-серверов (таблица Windows удалённую сторону
   UDP не знает — это честно написано и в коде, и в отчёте пользователю), затем сам сетевой слой: WinDivert
   только динамической загрузкой + THIRD-PARTY-NOTICES, узкий 5-tuple фильтр, факт маркировки DSCP,
   маршруты через `CreateIpForwardEntry2` с точным откатом, гейт `AntiCheatCompatibilityProfile`.
3. **`PingForge.Service` — сделано ядро, остался бой на Windows:** протокол канала (кадр «4 байта длины +
   JSON», предел 1 МиБ, честные тексты на обрыв и перерос), таблица 12 команд с признаком «нужны права
   администратора», разборщик, который никогда не роняет связь ошибкой, правила доступа к каналу
   (служба и администраторы — полный доступ, пользователь — чтение и команды, «всем» и входу по сети — отказ)
   и «мозги» службы: применение пресета и ручного набора через каталог, откат из снапшота, хвост журнала,
   поиск остатков для «починить сеть». 92 автотеста (`ServiceProtocolTests`, `ServiceDispatcherTests`,
   `ServiceEngineTests`, `ServiceSecurityTests`). Написаны и компилируются, но проверяются только на Windows:
   канал с настоящим ACL (`PipeAclFactory`) и запуск как службы через диспетчер служб
   (`ServiceControlDispatcher`). **Сделано:** чтение состояния Windows и сети (проект
   `PingForge.SystemState`, `SystemStateReader`, 43 теста) и двенадцатая команда канала `system-state`;
   утилита живой проверки `tools/PingForge.EngineSmoke` — она говорит со службой тем же каналом, что окно,
   и на сборочной Windows проверяет весь путь целиком; установка, запуск и снятие службы проверяются
   в CI вместе с установщиком. Там же нашлась и настоящая ошибка: имя команды собиралось из имени
   значения перечисления, поэтому приложение отправляло `read-system-state`, а служба ждала `system-state`
   (и так же расходились «возврат настроек» — `rollback` против `rollback-snapshot`). Теперь имя берётся
   из таблицы команд, а тест прогоняет через JSON каждое значение перечисления.
   **Сделано в раунде поставки:** установщик NSIS собирается в CI (`makensis`), целиком проверяется
   на сборочной Windows (см. §1.2 — там же девять настоящих ошибок, найденных этой проверкой), и релиз
   `v0.3.0` содержит установщик, программу и службу отдельными `.exe`, два архива и `SHA256SUMS.txt`.
   **Осталось:** исполнитель откатов для «починить сеть», перезапуск канала, поведение в бою на машине
   пользователя.
4. **`PingForge.App` — сделано окно, остался запуск на Windows.** Интерфейс разделён на два проекта:
   `PingForge.App.ViewModels` (net10.0) — «интерфейс без интерфейса»: главный экран с одной кнопкой
   «Оптимизировать / Остановить и вернуть как было», раздел «Твики» (47 карточек, пресеты 19/5/23,
   массовый выбор), журнал, настройки, канал к службе со сверкой номера ответа. `PingForge.App`
   (net10.0-windows, WPF) — само окно: шапка с кнопкой «Поддержать автора», шесть разделов (включая «Игры»), мастер первого запуска,
   карточки твиков с «красивыми» ползунками и развёртыванием «Подробнее», значок в трее (меню собирается
   тем же `TrayMenuBuilder`, что покрыт тестами), диалоги подтверждения и файл настроек.
   47 тестов (`ViewModelTests`, `AppSettingsStoreTests`) проверяют именно решения интерфейса: что при запуске
   ничего не происходит, что «включить все» не включает твики с вердиктом «не советуем», что отмена
   в диалоге означает «ничего не менялось», что «не измерено» не превращается в «0 мс».
   **Осталось:** запустить окно на живой Windows, поправить отрисовку и шрифты, проверить значок в трее.
5. **Проверки на реальном железе** — три сценария отказа: убийство службы при применении твиков,
   перезагрузка с активным туннелем/маршрутом/драйвером, отзыв прав администратора.
6. **Установщик — сделан, осталась подпись.** `installer/CustomTweakByDoxaiz.nsi` (NSIS): обычный
   установщик одним .exe — файлы, служба, ярлыки, запись в «Программах и компонентах», удаление без следов
   и с сохранением журнала и снапшотов. Собирается в CI и там же проверяется. Кроме него релиз отдаёт
   отдельные .exe (программа и служба), два архива и `SHA256SUMS.txt` с контрольными суммами.
   **Осталось:** EV-сертификат обязателен, иначе SmartScreen и анти-читы
   будут реагировать на службу с драйвером.

Что осознанно вырезано из первой версии: дублирование пакетов (FEC) и многопутевая передача.
